# 4.6. Contexto de persistencia y ciclo de la transacción

> **Duración estimada:** 20 min (10 min teoría + 10 min práctica)

---

## 🧠 Teoría rápida (10 min)

Llevamos cinco secciones hablando de "contexto de persistencia" y "transacción" como si fueran lo mismo. **No lo son**. Esta sección desentrelaza los dos conceptos y explica por qué a veces parecen coincidir y por qué a veces no.

### Las dos cosas

**El contexto de persistencia (`persistence context`)** es **el mapa de entidades managed** que vive dentro de un `EntityManager`. Es la caché de primer nivel. Es lo que permite el dirty checking.

**La transacción** es la unidad atómica de trabajo contra la base de datos: o se hace todo o no se hace nada.

Las dos cosas tienen ciclos de vida **independientes**, aunque suelan coincidir.

### En JPA `RESOURCE_LOCAL` (lo nuestro)

El contexto vive **mientras vive el `EntityManager`**:

- `em.createEntityManager()` → contexto nuevo, vacío.
- Operaciones (`persist`, `find`...) → entidades managed van entrando.
- `em.close()` → contexto destruido, todas las entidades pasan a `detached`.

La transacción vive **entre `begin` y `commit`/`rollback`**:

- `tx.begin()` → transacción abierta en BD.
- SQL acumulado durante el trabajo (con `flush` automáticos antes de queries que lo requieran).
- `tx.commit()` → `flush` final + `COMMIT` SQL.
- `tx.rollback()` → `ROLLBACK` SQL.

> **Punto clave:** un `EntityManager` puede abrir y cerrar **varias transacciones** durante su vida, y el contexto se mantiene en medio. Lo viste en **4.5** con `dosTransaccionesMismoEm`.

### Las cuatro combinaciones posibles

| Caso | Contexto | Transacción | Comentario |
|------|----------|-------------|------------|
| 1 | Vivo | Activa | Caso normal: trabajo dentro de una unidad. |
| 2 | Vivo | Cerrada (tras commit) | Las entidades siguen managed pero no se persistirá nada hasta el siguiente `begin`. |
| 3 | Vivo | Cerrada (tras rollback) | Estado **delicado**: las entidades managed pueden estar desincronizadas con BD. Conviene `clear()` o cerrar el EM. |
| 4 | Cerrado | (n/a) | Tras `em.close()`. Todas las entidades, detached. |

### El patrón "una transacción por unidad de trabajo"

En 90% de los casos, el patrón es:

```
abrir EM → begin → trabajo → commit → cerrar EM
```

Un `EntityManager` por operación, una transacción por `EntityManager`. Simple, predecible, fácil de razonar. Es lo que hace `TxRunner` por dentro.

Las variantes (un EM, varias transacciones) existen pero son raras: procesos por lotes, operaciones interactivas largas, etc.

### Por qué importa esto

Porque cuando algo falla, **necesitas saber qué se quedó en qué estado**. Por ejemplo:

> "He hecho `persist`, ha saltado una excepción, ¿está la entidad en BD?"

Respuesta: depende de si se ejecutó el `commit`. Si saltó **antes** del commit, no. Si el commit lanzó la excepción, **a medias** (algunos SQL pueden haberse ejecutado pero todo se hace rollback). Tu helper transaccional debe garantizar el `rollback` en ese caso.

Y otra muy común:

> "He llamado a `find`, he cerrado el EM, y al acceder a una colección lazy salta `LazyInitializationException`."

Respuesta: claro. La entidad está detached, su colección lazy nunca se cargó, y sin contexto ya no puede cargarla. Si el contexto está cerrado, la pista se acabó. Esto lo trataremos a fondo en **4.7** y en el Bloque 5.

## 🛠️ Práctica guiada (10 min)

### Paso 1 — Comprobar que el contexto sobrevive al commit

Crea `com.pizzeria.sandbox.CicloVidaDemo`:

```java
package com.pizzeria.sandbox;

import com.pizzeria.infrastructure.JpaBootstrap;
import com.pizzeria.persistence.ingrediente.IngredienteJpa;
import jakarta.persistence.EntityManager;

import java.math.BigDecimal;

public class CicloVidaDemo {

    public static void main(String[] args) {
        try {
            contextoSobreviveCommit();
            entidadesQuedanDetachedAlCerrarEm();
        } finally {
            JpaBootstrap.shutdown();
        }
    }

    static void contextoSobreviveCommit() {
        System.out.println("\n--- Contexto sobrevive al commit ---");
        EntityManager em = JpaBootstrap.openEntityManager();

        em.getTransaction().begin();
        IngredienteJpa i = new IngredienteJpa();
        i.setNombre("Rúcula");
        i.setCoste(new BigDecimal("0.70"));
        em.persist(i);
        em.getTransaction().commit();

        System.out.println("Tras commit, ¿managed? " + em.contains(i));    // true
        System.out.println("Modificamos sin transacción nueva...");
        i.setCoste(new BigDecimal("0.90"));   // no se persistirá ya

        System.out.println("Abrimos nueva transacción...");
        em.getTransaction().begin();
        // El dirty checking detecta el cambio que hicimos fuera de transacción
        em.getTransaction().commit();

        IngredienteJpa releido = em.find(IngredienteJpa.class, i.getId());
        System.out.println("Coste final: " + releido.getCoste());   // 0.90

        em.close();
    }

    static void entidadesQuedanDetachedAlCerrarEm() {
        System.out.println("\n--- Tras close(), todo detached ---");
        EntityManager em = JpaBootstrap.openEntityManager();
        em.getTransaction().begin();
        IngredienteJpa i = new IngredienteJpa();
        i.setNombre("Pesto");
        i.setCoste(new BigDecimal("1.30"));
        em.persist(i);
        em.getTransaction().commit();
        Long id = i.getId();
        em.close();

        System.out.println("EM cerrado.");
        i.setCoste(new BigDecimal("99.99"));   // cambio en memoria, irrelevante

        EntityManager em2 = JpaBootstrap.openEntityManager();
        IngredienteJpa releido = em2.find(IngredienteJpa.class, id);
        System.out.println("Coste en BD: " + releido.getCoste());   // 1.30, no 99.99
        em2.close();
    }
}
```

Ejecuta y observa cómo:

- En la primera demo, el cambio se persiste porque la entidad seguía managed cuando abriste la segunda transacción.
- En la segunda, el cambio se pierde porque el EM ya estaba cerrado al modificar.

### Paso 2 — El estado "limbo" tras rollback

```java
static void traRollbackElContextoEstaSucio() {
    System.out.println("\n--- Estado tras rollback ---");
    EntityManager em = JpaBootstrap.openEntityManager();
    em.getTransaction().begin();

    IngredienteJpa i = new IngredienteJpa();
    i.setNombre("Trufa");
    i.setCoste(new BigDecimal("12.00"));
    em.persist(i);

    em.getTransaction().rollback();   // descartamos

    System.out.println("¿i sigue managed tras rollback? " + em.contains(i));
    // Nota: Hibernate suele dejar la entidad managed pero con id potencialmente inválido.
    // Lo más seguro tras rollback es clear() o close().

    em.clear();
    System.out.println("Tras clear(): " + em.contains(i));   // false

    em.close();
}
```

### Checkpoint

- [ ] Sabes que el contexto y la transacción tienen ciclos de vida distintos.
- [ ] Has visto que un `EntityManager` puede abrir varias transacciones.
- [ ] Sabes que tras `close()` todo queda detached, y tras `rollback` lo más seguro es `clear()`.

## 🎯 Cierre

El modelo "un EM, una transacción" funciona casi siempre y es el que vamos a usar a través de `TxRunner`. Pero conocer las costuras te permite explicar bugs raros y diseñar procesos por lotes cuando llegue el momento.

En **4.7** abordamos algo donde teoría y práctica se cruzan con fuerza: las **decisiones de carga** (lazy vs eager) y cómo se relacionan con tu modelo de agregados del Bloque 2.

> **Idea para llevarse:** el contexto no es la transacción. Son dos relojes distintos en el mismo `EntityManager`.
