# 4.4. Dirty checking

> **Duración estimada:** 20 min (8 min teoría + 12 min práctica)

---

## 🧠 Teoría rápida (8 min)

Ya lo has visto en acción dos veces (en **4.2** y en **4.3**): cambias un atributo de una entidad **managed**, no llamas a ningún método de actualización, y al hacer `commit` el cambio se guarda. Esto se llama **dirty checking** ("comprobación de suciedad").

### Cómo funciona por dentro

Cuando una entidad entra al contexto de persistencia (vía `persist`, `find`, una query…), Hibernate guarda una **snapshot** de sus atributos: una copia de los valores que tenía en ese momento.

En el momento del `flush` (o del `commit`, que internamente hace `flush`), Hibernate:

1. Recorre todas las entidades managed del contexto.
2. Para cada una, compara los **valores actuales** con los de la **snapshot**.
3. Si hay diferencias → emite `UPDATE` con esos campos.
4. Si no hay diferencias → no hace nada.

Por eso "no hace falta llamar a `update`". JPA ni siquiera tiene un método `update`. Lo que hay es **detección automática** al `flush`.

### Implicaciones que conviene tener claras

**No es magia, tiene coste.** Hibernate mantiene la snapshot de cada entidad managed. Cuantas más entidades, más memoria. Por eso `clear()` existe.

**Solo afecta a entidades managed.** Si tu entidad está detached y la modificas, el cambio se queda en RAM. Por eso `merge` existe.

**Detecta solo cambios en los atributos mapeados.** Si tienes un campo `@Transient`, no se compara ni se sincroniza.

**Comparación campo a campo.** Por defecto Hibernate compara todos los campos. Existen estrategias para optimizar esto en entidades enormes (`DynamicUpdate`), pero rara vez merecen la pena.

### El UPDATE selectivo (o no)

Por defecto, cuando Hibernate detecta un cambio, emite un `UPDATE` con **todos los campos** de la entidad, no solo los que han cambiado:

```sql
UPDATE ingrediente SET nombre=?, coste=? WHERE id=?
```

Esto sorprende a quien viene de SQL a pelo y espera ver `UPDATE ingrediente SET coste=? WHERE id=?`. Si te molesta de verdad, existe `@DynamicUpdate`, que compone el `UPDATE` con solo los campos sucios. Para entidades con pocos campos, no merece la pena.

### Por qué esto cambia tu mentalidad

Esto es lo que más cuesta interiorizar al venir de JDBC:

> En JDBC tú decides qué se actualiza, cuándo, y con qué `WHERE`. En JPA tú modificas objetos y JPA decide.

No es mejor ni peor, es **otro modelo de programación**. Pero hasta que no lo aceptas, sigues pensando "¿cuándo lanzo el `UPDATE`?", y la respuesta es "tú no lo lanzas".

## 🛠️ Práctica guiada (12 min)

### Paso 1 — Ver el UPDATE sin llamar a nada

Crea `com.pizzeria.sandbox.DirtyCheckingDemo`:

```java
package com.pizzeria.sandbox;

import com.pizzeria.infrastructure.JpaBootstrap;
import com.pizzeria.persistence.ingrediente.IngredienteJpa;
import jakarta.persistence.EntityManager;

import java.math.BigDecimal;

public class DirtyCheckingDemo {

    public static void main(String[] args) {
        try {
            crearIngrediente();
            modificarSinUpdate();
            comprobarCambio();
        } finally {
            JpaBootstrap.shutdown();
        }
    }

    static Long ingredienteId;

    static void crearIngrediente() {
        EntityManager em = JpaBootstrap.openEntityManager();
        em.getTransaction().begin();

        IngredienteJpa i = new IngredienteJpa();
        i.setNombre("Mozzarella");
        i.setCoste(new BigDecimal("1.20"));
        em.persist(i);
        em.getTransaction().commit();

        ingredienteId = i.getId();
        em.close();
        System.out.println("Creado id=" + ingredienteId);
    }

    static void modificarSinUpdate() {
        System.out.println("\n--- Modificación sin llamar a update ---");
        EntityManager em = JpaBootstrap.openEntityManager();
        em.getTransaction().begin();

        IngredienteJpa managed = em.find(IngredienteJpa.class, ingredienteId);
        managed.setCoste(new BigDecimal("1.40"));   // ÚNICA línea

        em.getTransaction().commit();   // ← aquí sale el UPDATE
        em.close();
    }

    static void comprobarCambio() {
        EntityManager em = JpaBootstrap.openEntityManager();
        IngredienteJpa releido = em.find(IngredienteJpa.class, ingredienteId);
        System.out.println("Coste tras commit: " + releido.getCoste());
        em.close();
    }
}
```

Al ejecutar, observa con `show_sql`:

- En `crearIngrediente`: `INSERT`.
- En `modificarSinUpdate`: `SELECT` (del `find`) seguido de **`UPDATE` en el `commit`**, sin que hayas llamado a nada parecido a `update`.
- En `comprobarCambio`: `SELECT` que devuelve `1.40`.

### Paso 2 — Confirmar que no hay UPDATE sin cambios

Añade este método:

```java
static void modificarSinCambioReal() {
    System.out.println("\n--- 'Modificación' que en realidad no cambia nada ---");
    EntityManager em = JpaBootstrap.openEntityManager();
    em.getTransaction().begin();

    IngredienteJpa managed = em.find(IngredienteJpa.class, ingredienteId);
    BigDecimal mismoCoste = managed.getCoste();
    managed.setCoste(mismoCoste);    // misma referencia / mismo valor

    em.getTransaction().commit();
    em.close();
}
```

> **Importante:** la comparación de Hibernate usa `equals`. Si pasas un `BigDecimal` que es `equals` al actual, no detecta cambio. Si pasas un `BigDecimal` que es **numéricamente igual pero con distinta escala** (`new BigDecimal("1.20")` vs `new BigDecimal("1.2")`), `equals` de `BigDecimal` los considera **distintos** y vas a ver un `UPDATE` aunque "no haya cambiado nada". Un clásico.

### Paso 3 — Dirty checking sobre una entidad detached: no pasa nada

```java
static void modificarDetached() {
    System.out.println("\n--- Modificación de entidad detached ---");
    EntityManager em = JpaBootstrap.openEntityManager();
    IngredienteJpa detached = em.find(IngredienteJpa.class, ingredienteId);
    em.close();   // detached desde aquí

    detached.setCoste(new BigDecimal("999.99"));
    System.out.println("Cambio en RAM: " + detached.getCoste());

    EntityManager em2 = JpaBootstrap.openEntityManager();
    IngredienteJpa releido = em2.find(IngredienteJpa.class, ingredienteId);
    System.out.println("Lo que hay en BD: " + releido.getCoste());
    em2.close();
}
```

Salida:

```
Cambio en RAM: 999.99
Lo que hay en BD: 1.40
```

El cambio se queda en RAM. Sin contexto, no hay dirty checking. Si querías guardarlo, tendrías que haber hecho `merge`.

### Paso 4 — Mini-reto

Predice la salida antes de ejecutarla:

```java
EntityManager em = JpaBootstrap.openEntityManager();
em.getTransaction().begin();

IngredienteJpa ing = em.find(IngredienteJpa.class, ingredienteId);
ing.setCoste(new BigDecimal("5.00"));
em.flush();                              // ¿qué SQL sale aquí?
ing.setCoste(new BigDecimal("7.00"));
em.flush();                              // ¿y aquí?
em.getTransaction().rollback();          // ¿y al final qué quedó en BD?

em.close();
```

> *Respuesta:*
> Primer `flush` → `UPDATE coste=5.00`.
> Segundo `flush` → `UPDATE coste=7.00`.
> `rollback` → la transacción se deshace, en BD vuelve a estar `1.40`.
> Los `flush` adelantan SQL pero no confirman: el `rollback` revierte todo.

### Checkpoint

- [ ] Has visto un `UPDATE` ejecutarse sin que llames a nada parecido a `update`.
- [ ] Sabes que sobre una entidad detached el dirty checking no aplica.
- [ ] Has comprobado que `flush` adelanta SQL pero no confirma.
- [ ] (Bonus) Sabes que `BigDecimal` con distinta escala dispara `UPDATE` falsos.

## 🎯 Cierre

El dirty checking es **el mecanismo central** de JPA. Una vez lo entiendes, dejas de pelearte con la API y empiezas a confiar en ella. Pero también es la fuente del *"se ha guardado algo que no quería"*: si tu entidad está managed, cualquier `setter` que ejecutes va a impactar BD al commit.

> **Idea para llevarse:** en JPA no se hace `UPDATE`. Se modifica un objeto managed y se confía. Eso es bonito y peligroso a partes iguales.

En **4.5** entramos en transacciones: el otro pilar imprescindible para que todo esto tenga sentido.
