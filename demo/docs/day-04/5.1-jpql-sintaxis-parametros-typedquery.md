# 5.1 · JPQL: sintaxis, parámetros, `TypedQuery`

## El problema que JPQL viene a resolver

Hasta aquí hemos trabajado el ciclo CRUD básico contra un único agregado: `persist`, `find`, `merge`, `remove`. Esto es suficiente para muchas cosas, pero se rompe en cuanto aparece la primera pregunta de negocio real:

> "Dame todas las pizzas cuyo precio calculado supere los 12 €, ordenadas alfabéticamente."

`find` no sirve: solo localiza por identidad. Necesitamos **consultas**. Y ahora aparece la tentación: *"si lo que hay debajo es SQL, ¿por qué no escribo SQL?"*

La respuesta vuelve a la decisión arquitectónica del Bloque 1. Si escribimos SQL aquí:

- Acoplamos el código al dialecto concreto (H2, PostgreSQL, MySQL).
- Trabajamos sobre **filas y columnas**, no sobre **entidades**.
- Perdemos el contexto de persistencia: los resultados no entran como entidades gestionadas.
- Renunciamos a la validación de la query en tiempo de compilación contra el modelo.

JPQL es la respuesta de la especificación: un lenguaje de consultas que se **parece** a SQL pero que opera sobre el **modelo de entidades**, no sobre las tablas.

## Qué es JPQL exactamente

JPQL (Java Persistence Query Language) es un lenguaje orientado a objetos. Las diferencias con SQL son importantes y conviene fijarlas pronto:

| SQL | JPQL |
|---|---|
| Opera sobre tablas | Opera sobre entidades |
| `SELECT * FROM pizza` | `SELECT p FROM PizzaEntity p` |
| Usa nombres de columna | Usa nombres de atributo Java |
| Devuelve filas | Devuelve entidades (o proyecciones) |
| Sensible al dialecto | Portable entre proveedores |

Detalle a recalcar: en JPQL el `FROM` se refiere al **nombre de la entidad**, no de la tabla. Si nuestra clase es `PizzaEntity` mapeada a la tabla `pizza`, la consulta usa `PizzaEntity`. Esto lo demuestran bien los errores típicos del primer día: `org.hibernate.query.SemanticException: Could not resolve entity 'pizza'`.

## La consulta más básica

```java
String jpql = "SELECT p FROM PizzaEntity p";

TypedQuery<PizzaEntity> query = em.createQuery(jpql, PizzaEntity.class);
List<PizzaEntity> pizzas = query.getResultList();
```

Tres cosas que merecen detenerse:

**1. El alias `p` es obligatorio.** JPQL no admite `SELECT FROM PizzaEntity`. La gramática exige un identificador de variable.

**2. `SELECT p` devuelve entidades gestionadas.** No filas. No DTOs. Entidades. Cada una pasa al contexto de persistencia y a partir de ese momento aplica el `dirty checking` que vimos en 4.4. Si modificamos uno de esos objetos dentro de la transacción, al hacer `commit` se hará `UPDATE` automáticamente.

**3. `createQuery` tiene dos sobrecargas.** La que recibe solo un `String` devuelve `Query` (sin tipo). La que recibe `String` y `Class<T>` devuelve `TypedQuery<T>`. Hablaremos de esto enseguida.

## `Query` vs `TypedQuery`: por qué `TypedQuery` casi siempre

La interfaz `Query` es la original. Su firma es esencialmente:

```java
List getResultList();   // sin genéricos
Object getSingleResult();
```

Esto significa que hay que castear:

```java
Query query = em.createQuery("SELECT p FROM PizzaEntity p");
List<PizzaEntity> pizzas = (List<PizzaEntity>) query.getResultList(); // unchecked warning
```

`TypedQuery<T>` se introdujo en JPA 2.0 precisamente para evitar este olor:

```java
TypedQuery<PizzaEntity> query = em.createQuery(
    "SELECT p FROM PizzaEntity p", PizzaEntity.class);
List<PizzaEntity> pizzas = query.getResultList(); // tipado
```

Regla práctica: **usar siempre `TypedQuery`**, salvo en queries de actualización masiva (`UPDATE`/`DELETE` JPQL), donde no hay resultado tipado que devolver y se usa `Query` con `executeUpdate()`. Lo veremos en 5.3.

## Parámetros: nunca concatenar

Llega la primera consulta filtrada. La tentación es la misma de siempre:

```java
// MAL
String jpql = "SELECT p FROM PizzaEntity p WHERE p.nombre = '" + nombre + "'";
```

Esto es inyección JPQL. Aunque JPQL no se traduce directamente a SQL al pie de la letra (el proveedor interpreta el árbol semántico), concatenar entradas externas sigue siendo una vulnerabilidad real y un error grave de diseño. JPA ofrece **dos formas** de parametrizar:

### Parámetros nombrados (recomendado)

```java
TypedQuery<PizzaEntity> query = em.createQuery(
    "SELECT p FROM PizzaEntity p WHERE p.nombre = :nombre",
    PizzaEntity.class);
query.setParameter("nombre", "Margarita");
List<PizzaEntity> resultado = query.getResultList();
```

Los nombrados ganan en legibilidad y en queries con varias condiciones. Si una pizza filtrara por nombre y por rango de fechas, el nombre dice qué es cada parámetro.

### Parámetros posicionales

```java
TypedQuery<PizzaEntity> query = em.createQuery(
    "SELECT p FROM PizzaEntity p WHERE p.nombre = ?1",
    PizzaEntity.class);
query.setParameter(1, "Margarita");
```

Funcionan. Pero no aportan nada que los nombrados no hagan mejor. Conviene saber que existen porque los veremos en código heredado.

> **Decisión de curso:** parámetros nombrados por defecto. Posicionales solo como excepción justificada.

## Obtener un único resultado

```java
TypedQuery<PizzaEntity> query = em.createQuery(
    "SELECT p FROM PizzaEntity p WHERE p.nombre = :nombre",
    PizzaEntity.class);
query.setParameter("nombre", "Margarita");

PizzaEntity pizza = query.getSingleResult();
```

`getSingleResult()` lanza dos excepciones bien diferenciadas y conviene conocerlas:

- `NoResultException`: la query no devolvió nada.
- `NonUniqueResultException`: la query devolvió más de un resultado.

Ambas son **runtime** y revientan la transacción. Si esperamos que "puede no haber resultado", el patrón limpio es:

```java
List<PizzaEntity> resultados = query.getResultList();
PizzaEntity pizza = resultados.isEmpty() ? null : resultados.get(0);
```

O, en proyectos modernos, envolverlo en `Optional`. Spring Data JPA hace esto por nosotros, pero conviene tener claro que la API base no devuelve `Optional` en `getSingleResult`.

## Proyecciones: no siempre queremos la entidad entera

Hay consultas en las que no necesitamos la pizza completa: solo su nombre y su precio. Cargar el agregado entero por un dato sería desperdiciar memoria y bloquear filas innecesariamente. JPQL admite proyecciones:

### Proyección a `Object[]`

```java
TypedQuery<Object[]> query = em.createQuery(
    "SELECT p.nombre, p.id FROM PizzaEntity p", Object[].class);
List<Object[]> filas = query.getResultList();
for (Object[] fila : filas) {
    String nombre = (String) fila[0];
    PizzaId id = (PizzaId) fila[1];
}
```

Funciona pero es feo. Sin tipos. Sin nombres. Es el equivalente a programar con tuplas anónimas.

### Proyección a DTO con constructor

```java
public record PizzaResumenDto(String nombre, PizzaId id) {}
```

```java
TypedQuery<PizzaResumenDto> query = em.createQuery(
    "SELECT new com.pizzeria.dto.PizzaResumenDto(p.nombre, p.id) " +
    "FROM PizzaEntity p", PizzaResumenDto.class);
List<PizzaResumenDto> resumen = query.getResultList();
```

Esta sintaxis (`SELECT new ...`) exige el **nombre completamente cualificado** de la clase y un constructor cuyos tipos coincidan exactamente con los devueltos por la query. Los records funcionan perfectamente porque sintetizan el constructor canónico.

> **Punto importante:** los DTOs proyectados **no** entran al contexto de persistencia. No son entidades. No tienen `dirty checking`. Son datos. Y eso es exactamente lo que queremos para consultas de lectura: leer y olvidar.

## Detalle sobre `Money` y los value objects

Como nuestros precios son `Money` (un `record` `@Embeddable`), JPQL accede a los campos del embebido con notación punteada:

```java
// Suponiendo que IngredienteEntity tiene un Money llamado coste
em.createQuery(
    "SELECT i FROM IngredienteEntity i WHERE i.coste.cantidad > :limite",
    IngredienteEntity.class
).setParameter("limite", new BigDecimal("2.50"));
```

El `record` `Money(BigDecimal cantidad, String moneda)` expone `cantidad` como campo navegable en JPQL. Es uno de los puntos donde el modelado del Bloque 2 paga dividendos: el dominio sigue siendo expresivo y la consulta también.

## Resumen de la sección

- JPQL trabaja sobre **entidades**, no tablas. El alias es obligatorio.
- `TypedQuery<T>` por defecto. `Query` solo para `UPDATE`/`DELETE` masivos.
- Parámetros **siempre** vía `setParameter`. Nombrados sobre posicionales.
- `getSingleResult()` lanza excepción si hay 0 o >1 resultados.
- Para datos parciales: proyectar a DTO con `SELECT new`. Los DTOs no son entidades.
- Los `@Embeddable` se navegan con punto, como cualquier otro atributo.
