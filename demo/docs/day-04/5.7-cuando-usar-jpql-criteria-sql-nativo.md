# 5.7 · Cuándo usar JPQL, Criteria o SQL nativo

## Recapitulando con honestidad

A estas alturas el alumno tiene en la cabeza tres herramientas para consultar:

- **JPQL**: orientado a entidades, portable, legible.
- **Criteria API**: programático, tipado, para queries dinámicas.
- **SQL nativo**: directo a la BD, sin abstracción, máxima potencia.

Una de las preguntas más recurrentes al terminar el bloque es: *"Vale, ya entiendo cada uno, ¿pero cuándo uso cuál?"*. Esta sección está pensada como cierre del subbloque de consultas, antes de entrar en errores comunes. Su función es **dejar reglas claras de decisión** y desactivar las trampas habituales.

## El criterio principal: dejar que la consulta hable

La pregunta no es *"¿qué herramienta prefiero?"*. Es *"¿qué naturaleza tiene esta consulta?"*. Tres rasgos guían la decisión:

1. **¿Es fija o dinámica?** (¿La forma de la query depende de parámetros opcionales?)
2. **¿Trabaja con entidades o con datos derivados?** (¿Devuelve filas que encajan en mi modelo, o agregaciones, reportes, vistas?)
3. **¿Necesita capacidades específicas del motor?** (Window functions, CTEs, JSON, geoespaciales...)

Con esas tres preguntas, la mayoría de decisiones se resuelven solas.

## El árbol de decisión

```
¿La consulta usa capacidades del dialecto que JPQL no expresa?
├── SÍ  →  SQL nativo (con mapeo a DTO)
└── NO
    │
    ¿La forma de la consulta es dinámica (filtros opcionales)?
    ├── SÍ  →  Criteria API
    │          (o Specifications si hay Spring Data)
    └── NO
        │
        ¿Devuelve entidades del modelo o datos derivados (sumas, conteos)?
        ├── ENTIDADES       →  JPQL + TypedQuery<Entity>
        └── DATOS DERIVADOS →  JPQL + SELECT new ... (proyección a DTO)
```

Esto cubre el 95% de los casos.

## Casos concretos del dominio pizzería

Bajemos el árbol a ejemplos reales del curso:

### Caso 1 · Listar todas las pizzas

> "Quiero todas las pizzas con sus ingredientes para mostrar en la carta."

Fija (sin filtros), devuelve entidades. → **JPQL** con `JOIN FETCH`.

```java
em.createQuery(
    "SELECT p FROM PizzaEntity p JOIN FETCH p.ingredientes",
    PizzaEntity.class
).getResultList();
```

### Caso 2 · Buscador de pizzas con filtros

> "El usuario puede filtrar por nombre, por precio mínimo, por ingrediente. Cualquier combinación."

Dinámica, entidades. → **Criteria** (o Specifications si hay Spring Data).

### Caso 3 · Top 5 pizzas más comentadas

> "Necesito un ranking con nombre de pizza y número de comentarios."

Fija, datos derivados (no son `PizzaEntity`: son `String + Long`). → **JPQL con `SELECT new`**.

```java
em.createQuery(
    "SELECT new com.pizzeria.dto.RankingPizzaDto(p.nombre, COUNT(c.id)) " +
    "FROM PizzaEntity p LEFT JOIN p.comments c " +
    "GROUP BY p.nombre " +
    "ORDER BY COUNT(c.id) DESC",
    RankingPizzaDto.class
).setMaxResults(5).getResultList();
```

### Caso 4 · Ranking con ventana: posición dentro de cada categoría

> "Para cada categoría de pizza, quiero las tres más caras con su posición."

JPQL no tiene `ROW_NUMBER() OVER (PARTITION BY ...)`. → **SQL nativo**.

```sql
SELECT * FROM (
  SELECT p.nombre, p.categoria, p.precio,
         ROW_NUMBER() OVER (PARTITION BY p.categoria ORDER BY p.precio DESC) AS rn
  FROM pizza p
) sub
WHERE sub.rn <= 3
```

### Caso 5 · Marcar inactivos todos los usuarios sin comentarios

> "Actualizar miles de filas a la vez."

Operación masiva, no devuelve resultados. → **JPQL `UPDATE`** (o nativo si JPQL se queda corto).

## Trampas frecuentes y cómo evitarlas

### Trampa 1: usar SQL nativo "porque me lo sé"

Esto pasa mucho con perfiles SQL fuertes. La excusa típica: *"para qué aprender JPQL si yo SQL me lo sé al dedillo"*. El coste:

- Pierdes portabilidad.
- Pierdes la integración con el contexto de persistencia.
- Las queries no se benefician del cache de segundo nivel (si está activo).
- Cualquier refactor de modelo no toca la query, hasta que revienta en producción.

JPQL no es "SQL para principiantes": es **SQL para el modelo de entidades**. Saber SQL es un activo, pero no excusa para evitar JPQL.

### Trampa 2: usar Criteria por sistema porque "es más seguro"

Otra trampa de equipo experimentado. *"Como Criteria está tipado, lo uso siempre, así me evito errores."* El coste:

- Triplicas el código de cada query.
- Reduces drásticamente la legibilidad.
- El "tipado" es mentira sin el metamodel estático.
- El próximo programador que lo mantenga llorará.

Criteria por defecto es overengineering. **JPQL fijo + Criteria solo cuando es dinámico** es la regla.

### Trampa 3: confundir "consulta" con "informe"

Las consultas operacionales (las que sirven al caso de uso del día a día) y los informes (agregaciones, vistas analíticas) son **distintos animales**.

- **Operacional**: pocas filas, entidades, mutaciones posteriores. → JPQL.
- **Reporting**: muchas filas, agregaciones, lectura pura. → JPQL con proyección o SQL nativo.

Forzar reporting a través del modelo de entidades es ineficiente y rompe la separación entre lectura y escritura que cualquier sistema medianamente grande acaba teniendo.

### Trampa 4: pensar que "performance" es siempre el criterio

A veces lo es. La mayoría de las veces, no. La diferencia entre JPQL y SQL nativo en una query bien formada y con índices es **despreciable**. Lo que mata el rendimiento no es la elección de herramienta: es el N+1, las queries sin índice, los `JOIN FETCH` a colecciones grandes paginados en memoria.

Optimizar la elección JPQL/nativo antes de medir es perder el tiempo.

## Una nota sobre la mantenibilidad

En proyectos reales, el código se lee 10 veces más de lo que se escribe. Esa proporción debería pesar en cada decisión:

- JPQL fija una **expectativa común** en el equipo: "las consultas se leen así".
- SQL nativo disperso por el código **rompe esa expectativa** y obliga al lector a cambiar de paradigma constantemente.
- Criteria es **el camino corto al "esto solo lo entendía Fulanito"**.

No es un argumento ortodoxo, pero es real: la decisión técnica más mantenible suele ser la más uniforme.

## La regla en una línea

> **JPQL por defecto. Criteria si es dinámica. Nativo si JPQL no puede o si es reporting.**

Si el alumno se queda con esa frase, ya tiene el 90% de las decisiones cubiertas.

## Resumen de la sección

- **JPQL** es la opción por defecto: portable, legible, integrada con el modelo.
- **Criteria** solo cuando la consulta es dinámica.
- **SQL nativo** cuando JPQL no llega o estamos en reporting puro.
- Trampas a evitar: nativo por costumbre, Criteria por sobreingeniería, confundir consulta operacional con reporting, optimizar sin medir.
- La uniformidad gana: facilita la lectura y el mantenimiento.

En 5.8 atacamos los errores más comunes: lo que se rompe cuando uno aplica todo esto sin entenderlo del todo.
