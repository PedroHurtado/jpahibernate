# 4.5. Transacciones: `EntityTransaction`, `begin`, `commit`, `rollback`

> **Duración estimada:** 25 min (8 min teoría + 17 min práctica)

---

## 🧠 Teoría rápida (8 min)

Hasta ahora hemos arrastrado un patrón sin desmenuzarlo:

```java
em.getTransaction().begin();
// ... trabajo ...
em.getTransaction().commit();
```

Hoy le ponemos nombre, le añadimos `rollback`, y entendemos por qué **sin transacción JPA no hace nada útil**.

### Qué es `EntityTransaction`

Es la API de transacciones de JPA cuando trabajas **fuera de un contenedor JEE** (cuando no hay un servidor de aplicaciones gestionándolas). Se obtiene con `em.getTransaction()` y tiene cuatro métodos relevantes:

- **`begin()`** — abre la transacción. A partir de aquí, los `INSERT`/`UPDATE`/`DELETE` que genere JPA se acumulan en una unidad atómica.
- **`commit()`** — confirma. Internamente hace `flush()` (vuelca el SQL pendiente al motor) y luego envía `COMMIT` a la BD.
- **`rollback()`** — descarta. Manda `ROLLBACK` a la BD; nada de lo hecho desde el `begin` queda.
- **`isActive()`** — útil para no llamar a `rollback` sobre una transacción ya cerrada (lo cual lanza `IllegalStateException`).

### Por qué sin transacción no se guarda nada

JPA con `RESOURCE_LOCAL` (que es lo que usamos al no tener contenedor) **exige una transacción activa** para hacer `persist`, `merge`, `remove`. Si intentas escribir sin transacción, te lanza `TransactionRequiredException`.

Las lecturas (`find`, queries) **sí** funcionan sin transacción activa. Pero es buena práctica abrirlas dentro de transacción de todos modos: garantizas snapshot consistente y haces que el flujo sea uniforme.

### El patrón canónico

```java
EntityManager em = JpaBootstrap.openEntityManager();
EntityTransaction tx = em.getTransaction();
try {
    tx.begin();
    // ... trabajo ...
    tx.commit();
} catch (RuntimeException e) {
    if (tx.isActive()) {
        tx.rollback();
    }
    throw e;
} finally {
    em.close();
}
```

Cinco cosas que **no** se deben hacer:

1. **No llamar a `rollback` sin comprobar `isActive`.** Si la transacción ya hizo commit (o nunca empezó), salta excepción.
2. **No anidar transacciones.** `EntityTransaction` no es reentrante. Llamar a `begin` con una ya activa lanza excepción.
3. **No olvidar el `finally em.close()`.** Si no cierras, fugas conexión.
4. **No tragarte la excepción.** Tras `rollback`, **relánzala**. Si no, tu código de aplicación cree que todo fue bien.
5. **No mezclar varios `EntityManager` en la misma transacción lógica.** Cada `EntityManager` tiene su propia transacción.

### Where does Spring fit?

En proyectos Spring se usa `@Transactional` y nada de `getTransaction()` a mano. Pero en este curso estamos a propósito en **JPA puro**, sin Spring. Entender el patrón a mano es lo que te permitirá luego entender qué hace Spring por debajo.

## 🛠️ Práctica guiada (17 min)

Vamos a montar un pequeño helper transaccional y a usarlo. Por el camino, observaremos qué pasa cuando rompemos las reglas.

### Paso 1 — Un helper transaccional

Crea `com.pizzeria.infrastructure.TxRunner`:

```java
package com.pizzeria.infrastructure;

import jakarta.persistence.EntityManager;
import jakarta.persistence.EntityTransaction;

import java.util.function.Consumer;
import java.util.function.Function;

public final class TxRunner {

    private TxRunner() {}

    /** Ejecuta una acción dentro de una transacción y devuelve un resultado. */
    public static <T> T inTransaction(Function<EntityManager, T> action) {
        EntityManager em = JpaBootstrap.openEntityManager();
        EntityTransaction tx = em.getTransaction();
        try {
            tx.begin();
            T result = action.apply(em);
            tx.commit();
            return result;
        } catch (RuntimeException e) {
            if (tx.isActive()) {
                tx.rollback();
            }
            throw e;
        } finally {
            em.close();
        }
    }

    /** Variante para acciones sin resultado. */
    public static void runInTransaction(Consumer<EntityManager> action) {
        inTransaction(em -> { action.accept(em); return null; });
    }
}
```

Este helper se va a usar muchas veces a partir de ahora. Encapsula el patrón canónico para que no se repita en cada llamada.

### Paso 2 — Usarlo

```java
package com.pizzeria.sandbox;

import com.pizzeria.infrastructure.JpaBootstrap;
import com.pizzeria.infrastructure.TxRunner;
import com.pizzeria.persistence.ingrediente.IngredienteJpa;

import java.math.BigDecimal;

public class TransaccionesDemo {

    public static void main(String[] args) {
        try {
            Long id = crearConTxRunner();
            System.out.println("Creado id=" + id);
        } finally {
            JpaBootstrap.shutdown();
        }
    }

    static Long crearConTxRunner() {
        return TxRunner.inTransaction(em -> {
            IngredienteJpa i = new IngredienteJpa();
            i.setNombre("Albahaca");
            i.setCoste(new BigDecimal("0.40"));
            em.persist(i);
            return i.getId();
        });
    }
}
```

Mucho más limpio que el patrón a pelo.

### Paso 3 — Provocar un rollback

Añade este método al sandbox:

```java
static void provocarRollback() {
    System.out.println("\n--- Provocando rollback ---");
    try {
        TxRunner.runInTransaction(em -> {
            IngredienteJpa i = new IngredienteJpa();
            i.setNombre("Atún");
            i.setCoste(new BigDecimal("2.00"));
            em.persist(i);

            // Forzamos un fallo a propósito:
            throw new IllegalStateException("Algo salió mal en la lógica de negocio");
        });
    } catch (IllegalStateException e) {
        System.out.println("Excepción capturada: " + e.getMessage());
    }

    // ¿se guardó el atún?
    Long count = TxRunner.inTransaction(em ->
        em.createQuery("SELECT COUNT(i) FROM IngredienteJpa i WHERE i.nombre = :n", Long.class)
          .setParameter("n", "Atún")
          .getSingleResult()
    );
    System.out.println("Atunes en BD tras rollback: " + count);
}
```

Salida esperada:

```
Excepción capturada: Algo salió mal en la lógica de negocio
Atunes en BD tras rollback: 0
```

El `INSERT` no llegó a confirmarse. La transacción se descartó. **Eso es lo que da sentido a tenerlas.**

### Paso 4 — El intento sin transacción

```java
static void intentarSinTransaccion() {
    System.out.println("\n--- Intento sin transacción ---");
    var em = JpaBootstrap.openEntityManager();
    try {
        IngredienteJpa i = new IngredienteJpa();
        i.setNombre("Anchoa");
        i.setCoste(new BigDecimal("1.20"));
        em.persist(i);  // ← debería fallar
    } catch (Exception e) {
        System.out.println("Tipo de excepción: " + e.getClass().getSimpleName());
        System.out.println("Mensaje: " + e.getMessage());
    } finally {
        em.close();
    }
}
```

Verás un `TransactionRequiredException`. JPA es explícito: **sin transacción no escribe**.

### Paso 5 — Observar qué pasa con dos transacciones consecutivas en el mismo EntityManager

```java
static void dosTransaccionesMismoEm() {
    System.out.println("\n--- Dos transacciones consecutivas en el mismo EM ---");
    var em = JpaBootstrap.openEntityManager();
    try {
        em.getTransaction().begin();
        IngredienteJpa a = new IngredienteJpa();
        a.setNombre("Maíz");
        a.setCoste(new BigDecimal("0.20"));
        em.persist(a);
        em.getTransaction().commit();
        System.out.println("Maíz committed, id=" + a.getId());
        System.out.println("¿Maíz sigue managed? " + em.contains(a));

        em.getTransaction().begin();
        a.setCoste(new BigDecimal("0.25"));   // ¿se actualiza?
        em.getTransaction().commit();

        var releido = em.find(IngredienteJpa.class, a.getId());
        System.out.println("Coste tras segunda tx: " + releido.getCoste());
    } finally {
        em.close();
    }
}
```

Observación importante: tras el `commit`, la entidad sigue **managed**. El contexto de persistencia no se vacía con el commit; lo que se cierra es la transacción. Eso permite seguir trabajando con la entidad y que el dirty checking de la segunda transacción detecte el cambio.

- [ ] Has integrado `TxRunner` en tu proyecto.

- [ ] Has visto el `TransactionRequiredException` cuando no hay transacción.

## 🎯 Cierre

Las transacciones de JPA no son ningún misterio: `begin`, `commit`, `rollback` y a correr. Pero el patrón de try/catch/finally es lo bastante propenso a errores como para que merezca la pena encapsularlo en un helper como `TxRunner`. A partir de aquí, todos los repositorios del proyecto van a vivir dentro de `TxRunner.inTransaction(...)`.

En **4.6** vamos a relacionar **contexto de persistencia** y **transacción**: dos cosas que coinciden mucho en la práctica pero no son lo mismo, y entender la diferencia te ahorra muchos bugs.

> **Idea para llevarse:** sin transacción, JPA no escribe. Con `TxRunner`, el patrón canónico se reduce a una llamada.
