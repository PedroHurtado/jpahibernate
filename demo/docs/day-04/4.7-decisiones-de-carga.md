# 4.7. Decisiones de carga: lazy en comentarios, agregado completo en ingredientes

> **Duración estimada:** 30 min (8 min teoría + 22 min práctica)

---

## 🧠 Teoría rápida (8 min)

Esta sección es donde **el modelo de agregados del Bloque 2** se cruza con **el ciclo de vida del contexto del Bloque 4**. La pregunta que vamos a responder:

> *Cuando cargo una `Pizza`, ¿se cargan también sus ingredientes? ¿Y sus comentarios?*

La respuesta no es técnica: es **arquitectónica**. Y la decimos desde el Bloque 2.

### Recordatorio: los agregados

En el Bloque 2 decidimos:

- **`Ingrediente` está dentro del agregado `Pizza`.** Una pizza sin sus ingredientes está incompleta: no podemos calcular su precio, no podemos mostrarla en el menú, no podemos validar invariantes. Pizza e ingredientes viajan juntos.
- **`Comment` está fuera del agregado `Pizza`.** Una pizza puede existir sin un solo comentario. Los comentarios son un agregado aparte, con su propia raíz, y se consultan por separado cuando hace falta.

### La traducción a JPA

Esta decisión de modelado se traduce a JPA así:

- **Ingredientes → EAGER, o LAZY + `JOIN FETCH` siempre.** Cuando un repositorio devuelve una `Pizza`, debe devolverla con sus ingredientes ya cargados. Si no, ha "mentido": ha devuelto media pizza.
- **Comentarios → LAZY siempre.** El `PizzaRepository` no carga comentarios. Los comentarios los pide el `CommentRepository` cuando se necesitan. **Nunca** los cargamos junto con la pizza.

### Por qué `LAZY` por defecto en todas las relaciones

Esta es una regla profesional **no negociable**:

> Todas las relaciones (`@ManyToOne`, `@OneToMany`, `@ManyToMany`, `@OneToOne`) se anotan con `fetch = FetchType.LAZY`.

Razones:

1. **Predecibilidad.** Los `EAGER` se "encadenan": una entidad EAGER carga otra EAGER que carga otra EAGER y de repente un `find` mete media base de datos en memoria.
2. **N+1.** EAGER esconde el problema dentro del `find`; LAZY lo hace visible al acceder.
3. **Control.** Con LAZY, el que sabe lo que necesita (el repositorio, mediante `JOIN FETCH`) decide qué cargar en cada caso.

### Cuándo cargas qué (decisión consciente)

Modelo de decisión:

- **Entidad raíz sin colecciones** (`Ingrediente`) → un simple `find`.
- **Entidad raíz con miembros del agregado** (`Pizza` + `Ingrediente`) → `find` + carga explícita del agregado vía `JOIN FETCH`. El método del repositorio devuelve la pizza ya inicializada.
- **Entidad raíz con asociación a otro agregado** (`Pizza` ← `Comment`) → `find` carga **solo** la pizza. Los comentarios los pide otro repositorio.

### Paso 1 — `IngredienteRepository`

Abre el esqueleto que dejaste en el Bloque 3 y rellénalo:

```java
package com.pizzeria.persistence.ingrediente;

import com.pizzeria.domain.ingrediente.Ingrediente;
import com.pizzeria.domain.ingrediente.IngredienteId;
import com.pizzeria.infrastructure.TxRunner;
import jakarta.persistence.EntityManager;

import java.util.List;
import java.util.Optional;

public class IngredienteRepository {

    private final IngredienteMapper mapper = new IngredienteMapper();

    public Ingrediente save(Ingrediente ingrediente) {
        return TxRunner.inTransaction(em -> {
            IngredienteJpa jpa = mapper.toJpa(ingrediente);
            if (jpa.getId() == null) {
                em.persist(jpa);
            } else {
                jpa = em.merge(jpa);
            }
            return mapper.toDomain(jpa);
        });
    }

    public Optional<Ingrediente> findById(IngredienteId id) {
        return TxRunner.inTransaction(em -> {
            IngredienteJpa jpa = em.find(IngredienteJpa.class, id.value());
            return Optional.ofNullable(jpa).map(mapper::toDomain);
        });
    }

    public List<Ingrediente> findAll() {
        return TxRunner.inTransaction(em ->
            em.createQuery("SELECT i FROM IngredienteJpa i", IngredienteJpa.class)
              .getResultList()
              .stream()
              .map(mapper::toDomain)
              .toList()
        );
    }

    public void delete(IngredienteId id) {
        TxRunner.runInTransaction(em -> {
            IngredienteJpa jpa = em.find(IngredienteJpa.class, id.value());
            if (jpa != null) {
                em.remove(jpa);
            }
        });
    }
}
```

> **Decisión:** `save` distingue entre nuevo (`id == null` → `persist`) y existente (`id != null` → `merge`). Esto es **una opción**, no la única. Otra alternativa, más limpia para algunos, sería tener dos métodos separados (`create` y `update`). Para este proyecto vamos con `save` único porque permite código de cliente más simple.

### Paso 3 — `PizzaRepository` con agregado completo

Aquí está la chicha de la sección. Una `Pizza` debe devolverse con sus ingredientes **ya cargados**. Tres opciones:

1. **`EAGER` en la relación.** Funciona pero pierdes control: TODA carga de pizza arrastra ingredientes, te guste o no.
2. **`LAZY` + acceso dentro de la transacción.** Funciona pero es frágil: si alguien cierra la transacción antes de acceder, `LazyInitializationException`.
3. **`LAZY` + `JOIN FETCH` en el query del repositorio.** Es la solución profesional: una sola query, un solo `SELECT` con join, la pizza llega con todo lo que prometemos.

Vamos con la (3):

```java
package com.pizzeria.persistence.pizza;

import com.pizzeria.domain.pizza.Pizza;
import com.pizzeria.domain.pizza.PizzaId;
import com.pizzeria.infrastructure.TxRunner;
import jakarta.persistence.NoResultException;

import java.util.List;
import java.util.Optional;

public class PizzaRepository {

    private final PizzaMapper mapper = new PizzaMapper();

    public Pizza save(Pizza pizza) {
        return TxRunner.inTransaction(em -> {
            PizzaJpa jpa = mapper.toJpa(pizza);
            if (jpa.getId() == null) {
                em.persist(jpa);
            } else {
                jpa = em.merge(jpa);
            }
            return mapper.toDomain(jpa);
        });
    }

    public Optional<Pizza> findById(PizzaId id) {
        return TxRunner.inTransaction(em -> {
            try {
                PizzaJpa jpa = em.createQuery("""
                        SELECT p FROM PizzaJpa p
                        LEFT JOIN FETCH p.ingredientes pi
                        LEFT JOIN FETCH pi.ingrediente
                        WHERE p.id = :id
                        """, PizzaJpa.class)
                    .setParameter("id", id.value())
                    .getSingleResult();
                return Optional.of(mapper.toDomain(jpa));
            } catch (NoResultException e) {
                return Optional.empty();
            }
        });
    }

    public List<Pizza> findAll() {
        return TxRunner.inTransaction(em ->
            em.createQuery("""
                    SELECT DISTINCT p FROM PizzaJpa p
                    LEFT JOIN FETCH p.ingredientes pi
                    LEFT JOIN FETCH pi.ingrediente
                    """, PizzaJpa.class)
              .getResultList()
              .stream()
              .map(mapper::toDomain)
              .toList()
        );
    }

    public void delete(PizzaId id) {
        TxRunner.runInTransaction(em -> {
            PizzaJpa jpa = em.find(PizzaJpa.class, id.value());
            if (jpa != null) {
                em.remove(jpa);
            }
        });
    }
}
```

Tres detalles importantes:

1. **`LEFT JOIN FETCH`** (no `JOIN`): así devolvemos también las pizzas sin ingredientes (raro, pero válido). Con `JOIN FETCH` a secas las perderías.
2. **Doble `JOIN FETCH`**: uno hacia la entidad asociativa `PizzaIngredienteJpa` y otro hacia `IngredienteJpa`. Es lo que requiere nuestro modelo N:M con atributos del Bloque 3.
3. **`DISTINCT`** en `findAll`: el JOIN multiplica filas (una pizza con 4 ingredientes produce 4 filas en el ResultSet); `DISTINCT` colapsa duplicados a nivel de entidad raíz.

### Paso 4 — Probar `PizzaRepository`

```java
public class PizzaRepoDemo {

    public static void main(String[] args) {
        try {
            // Primero asegurar que hay ingredientes en BD
            IngredienteRepository ingRepo = new IngredienteRepository();
            Ingrediente mozza = ingRepo.save(Ingrediente.create("Mozzarella", new BigDecimal("1.20")));
            Ingrediente tomate = ingRepo.save(Ingrediente.create("Tomate", new BigDecimal("0.80")));

            // Componer una pizza
            Pizza margarita = Pizza.create(
                "Margarita",
                List.of(
                    new IngredienteEnPizza(mozza, 1),
                    new IngredienteEnPizza(tomate, 1)
                )
            );

            PizzaRepository pizzaRepo = new PizzaRepository();
            Pizza guardada = pizzaRepo.save(margarita);
            System.out.println("Pizza guardada: " + guardada.nombre());

            // Releer
            pizzaRepo.findById(guardada.id()).ifPresent(p -> {
                System.out.println("Releída: " + p.nombre());
                System.out.println("Ingredientes (deben venir ya cargados):");
                p.ingredientes().forEach(i ->
                    System.out.println(" - " + i.ingrediente().nombre()));
                System.out.println("Precio calculado: " + p.precio().importe());
            });
        } finally {
            JpaBootstrap.shutdown();
        }
    }
}
```

> Adapta los constructores y métodos del dominio (`Pizza.create`, `IngredienteEnPizza`, etc) a la firma exacta que dejaste en el Bloque 2.

### Paso 5 — Demostrar que sin `JOIN FETCH` salta `LazyInitializationException`

Comenta temporalmente el `JOIN FETCH` del `findById` para que quede así:

```java
PizzaJpa jpa = em.find(PizzaJpa.class, id.value());
return Optional.of(mapper.toDomain(jpa));
```

Ejecuta de nuevo y observa: cuando el mapper intente convertir los ingredientes (fuera de la transacción, porque `TxRunner` ya cerró el EM), salta `LazyInitializationException`. **Es el bug clásico de JPA.** La cura es lo que acabamos de hacer: `JOIN FETCH` explícito en el repositorio.

Restaura el `JOIN FETCH` antes de seguir.
