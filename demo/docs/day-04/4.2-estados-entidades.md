# 4.2. Estados de las entidades: `transient`, `managed`, `detached`, `removed`

> **Duración estimada:** 25 min (10 min teoría + 15 min práctica)

---

## 🧠 Teoría rápida (10 min)

Esta sección es **la que separa al que cree que JPA "guarda objetos" del que entiende cómo funciona realmente**. Si te queda clara, el resto del bloque cae solo.

### El contexto de persistencia, una vez más

Cada `EntityManager` tiene su **contexto de persistencia**: un mapa interno `(EntityClass, Id) → instancia` con las entidades que está "vigilando" en ese momento. JPA llama a esto "managed entities".

Mientras una entidad esté en ese mapa:
- Cambios sobre sus atributos los va a detectar (eso es el **dirty checking** de **4.4**).
- Llamadas a `find(Pizza.class, id)` con el mismo id van a devolver **la misma instancia**, no una nueva.
- Al hacer `commit` (o `flush`), Hibernate sincroniza esos cambios contra la base de datos.

Si la entidad **no está** en ese mapa, JPA no la sigue. No detecta cambios, no sincroniza nada.

### Los cuatro estados

Una entidad puede estar en uno de cuatro estados según su relación con el contexto:

```
                            ┌──────────────┐
                            │  TRANSIENT   │   recién creada con new
                            │  (new)       │   no tiene id ni la conoce el EM
                            └──────┬───────┘
                                   │ persist()
                                   ▼
                            ┌──────────────┐
                ┌──────────►│   MANAGED    │   en el contexto
                │           │  (persistent)│   cambios sincronizados
                │           └──┬────────┬──┘
                │              │        │
                │     remove() │        │  detach() / clear() / close()
        merge() │              │        │
                │              ▼        ▼
                │           ┌─────────┐ ┌──────────────┐
                └───────────│ REMOVED │ │   DETACHED   │
                            │         │ │ (fuera del EM)│
                            └─────────┘ └──────────────┘
```

**`TRANSIENT`** — la entidad es un POJO recién hecho con `new`. No tiene id (o no está en BD), el `EntityManager` no la conoce.

**`MANAGED`** — el `EntityManager` la tiene en su contexto. Cualquier cambio sobre ella se va a propagar a BD en el próximo `flush`. Una entidad se vuelve `managed` por dos vías:
- Acaba de pasar por `persist(entidad)`.
- Acaba de salir de un `find()` o de una query.

**`DETACHED`** — la entidad **estuvo** en el contexto, pero ya no. Esto pasa cuando se cierra el `EntityManager`, cuando se llama `detach()` o `clear()`, o cuando otra `EntityManagerFactory` la creó en otra sesión. Sigue siendo un objeto válido con su id, pero los cambios **ya no se sincronizan**.

**`REMOVED`** — se ha llamado `remove(entidad)`. Está en el contexto, pero marcada para borrarse en el próximo `flush`.

### Por qué importa

Porque la pregunta más frecuente de cualquier alumno de JPA es:

> *"He cambiado un atributo y no se ha guardado, ¿por qué?"*

La respuesta casi siempre es: **porque la entidad no estaba `managed`**. O cerraste el `EntityManager` antes, o nunca llegaste a hacer `persist`, o leíste con un `EntityManager` y modificaste con otro.

La segunda pregunta más frecuente:

> *"He modificado un atributo y NO he llamado a `update`, ¿por qué se ha guardado?"*

Porque sí estaba `managed`, y JPA detectó el cambio. **Es el comportamiento esperado**, no un bug.

## 🛠️ Práctica guiada (15 min)

Vamos a inducir cada uno de los cuatro estados, observarlos, y comprobar que JPA se comporta como dice la teoría.

> **Pre-requisito:** las entidades del Bloque 3 deben estar en el classpath y tener el constructor sin argumentos `protected` que pide JPA. Si no las tienes así, esta práctica va a fallar.

### Paso 1 — Crear un sandbox

Crea `com.pizzeria.sandbox.EstadosDemo`:

```java
package com.pizzeria.sandbox;

import com.pizzeria.infrastructure.JpaBootstrap;
import com.pizzeria.persistence.ingrediente.IngredienteJpa;
import jakarta.persistence.EntityManager;

import java.math.BigDecimal;

public class EstadosDemo {

    public static void main(String[] args) {
        EntityManager em = JpaBootstrap.openEntityManager();
        try {
            em.getTransaction().begin();

            // 1) TRANSIENT
            IngredienteJpa ing = nuevoIngrediente("Mozzarella", new BigDecimal("1.20"));
            System.out.println("[TRANSIENT] ¿lo conoce el EM? " + em.contains(ing));

            // 2) MANAGED
            em.persist(ing);
            System.out.println("[MANAGED]   ¿lo conoce el EM? " + em.contains(ing));
            System.out.println("            id asignado: " + ing.getId());

            em.getTransaction().commit();

            // 3) DETACHED (cerramos el EM)
            em.close();
            System.out.println("[DETACHED]  EM cerrado, la entidad ya no está vigilada");

            // 4) MANAGED de nuevo (vía merge en un nuevo EM)
            EntityManager em2 = JpaBootstrap.openEntityManager();
            em2.getTransaction().begin();
            IngredienteJpa reattached = em2.merge(ing);
            System.out.println("[MANAGED]   tras merge en em2: " + em2.contains(reattached));
            System.out.println("            ¿es la misma instancia que 'ing'? " + (reattached == ing));

            // 5) REMOVED
            em2.remove(reattached);
            System.out.println("[REMOVED]   marcada para borrado, todavía en contexto: " + em2.contains(reattached));

            em2.getTransaction().commit();
            em2.close();

        } finally {
            JpaBootstrap.shutdown();
        }
    }

    private static IngredienteJpa nuevoIngrediente(String nombre, BigDecimal coste) {
        // Ajusta esto al constructor real que dejaste en IngredienteJpa al final del Bloque 3.
        IngredienteJpa i = new IngredienteJpa();
        i.setNombre(nombre);
        i.setCoste(coste);
        return i;
    }
}
```

> Si tu `IngredienteJpa` no tiene setters porque optaste por construirla solo vía el mapper, instánciala como en tu mapper. Lo importante es **tener una entidad nueva**, no la firma exacta del constructor.

### Paso 2 — Ejecutar y leer la salida

Salida esperada:

```
[TRANSIENT] ¿lo conoce el EM? false
[MANAGED]   ¿lo conoce el EM? true
            id asignado: 1
[DETACHED]  EM cerrado, la entidad ya no está vigilada
[MANAGED]   tras merge en em2: true
            ¿es la misma instancia que 'ing'? false
[REMOVED]   marcada para borrado, todavía en contexto: true
```

### Paso 3 — La trampa del `merge`

Fíjate especialmente en este detalle:

```
¿es la misma instancia que 'ing'? false
```

Esto sorprende mucho la primera vez. **`merge` no reattacha tu objeto**. Lo que hace es:

1. Toma tu objeto detached.
2. Busca (o crea) una **nueva instancia managed** con los datos copiados.
3. La devuelve.

El objeto original `ing` **sigue detached**. Por eso al hacer `merge` siempre se usa así:

```java
ing = em.merge(ing);  // sobrescribimos la referencia
```

Si lo haces sin reasignar, vas a seguir trabajando con la versión detached y los cambios no se guardarán. **Bug clásico**.

### Paso 4 — Mini-reto: "el cambio fantasma"

Añade este bloque al final de tu `main`, antes del `shutdown`:

```java
EntityManager em3 = JpaBootstrap.openEntityManager();
em3.getTransaction().begin();
IngredienteJpa nuevo = nuevoIngrediente("Albahaca", new BigDecimal("0.40"));
em3.persist(nuevo);
nuevo.setCoste(new BigDecimal("0.50"));   // ¡no llamamos a "update"!
em3.getTransaction().commit();
em3.close();
```

Pregunta: ¿qué valor de `coste` se guardó, `0.40` o `0.50`?

> *Respuesta:* `0.50`. Porque cuando hiciste `setCoste`, la entidad estaba **`managed`** y el dirty checking detectó el cambio antes del `commit`. **No hace falta llamar a `update` ni a `merge` con entidades managed**. Es uno de los comportamientos de JPA que más sorprenden y más confunden cuando no se entiende este modelo.

### Checkpoint

- [ ] Sabes inducir cada uno de los cuatro estados.
- [ ] Entiendes que `merge` devuelve una instancia nueva.
- [ ] Tienes claro que los cambios sobre una entidad `managed` se guardan sin llamadas explícitas.

## 🎯 Cierre

Los estados no son una curiosidad académica: son **el modelo mental sobre el que está construido todo JPA**. La sección **4.3** desmenuza cada operación (`persist`, `merge`, `find`, `remove`, `flush`, `refresh`, `detach`, `clear`) y la **4.4** profundiza en el dirty checking que acabas de presenciar.

> **Idea para llevarse:** JPA no guarda objetos; sincroniza un contexto. Si tu entidad no está en el contexto, no pasa nada.
