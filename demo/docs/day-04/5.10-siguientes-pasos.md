## Spring Data JPA: la siguiente parada natural

### Qué es

Spring Data JPA es un módulo de Spring que **automatiza el código repetitivo de repositorios**. En lugar de escribir:

```java
public class PizzaRepositoryImpl implements PizzaRepository {
    private final EntityManager em;
    
    public Optional<PizzaEntity> findById(PizzaId id) {
        return Optional.ofNullable(em.find(PizzaEntity.class, id));
    }
    
    public List<PizzaEntity> findByNombre(String nombre) {
        return em.createQuery(
            "SELECT p FROM PizzaEntity p WHERE p.nombre = :nombre",
            PizzaEntity.class
        ).setParameter("nombre", nombre).getResultList();
    }
    // ...
}
```

Se escribe:

```java
public interface PizzaRepository extends JpaRepository<PizzaEntity, PizzaId> {
    List<PizzaEntity> findByNombre(String nombre);
    Optional<PizzaEntity> findByNombreAndCategoria(String nombre, Categoria categoria);
    
    @Query("SELECT p FROM PizzaEntity p JOIN FETCH p.ingredientes WHERE p.id = :id")
    Optional<PizzaEntity> findByIdConIngredientes(@Param("id") PizzaId id);
}
```

La implementación se **genera en tiempo de arranque** mediante reflexión y proxies dinámicos. Los nombres de método se interpretan según convenciones (`findByX`, `countByY`, `existsByZ`), y para queries no triviales hay `@Query` con JPQL o nativo.

### Por qué tiene sentido tras este curso

Porque para entender qué hace Spring Data **necesitas saber JPA primero**. Cuando Spring Data genera `findByNombre`, está generando la query que tú aprenderías a escribir aquí. Cuando Spring Data abre y cierra una transacción con `@Transactional`, lo hace siguiendo el mismo patrón `begin/commit/rollback` del Bloque 4.

Sin la base de JPA, Spring Data es magia. Con la base, es **automatización**. La diferencia es enorme.

### Lo que también incluye

- `Pageable` y `Page<T>`: paginación con count automático.
- Specifications (que mencionamos en 5.5): queries dinámicas tipadas.
- Projections (interfaces o clases): proyecciones a DTO declarativas.
- Auditoría: `@CreatedDate`, `@LastModifiedDate`, `@CreatedBy` automáticos.
- Eventos de entidad: `@DomainEvents` para publicar al guardar.

### Coste a sopesar

Spring Data añade Spring al stack. Para muchos proyectos eso no es un coste: Spring ya estaba. Para librerías pequeñas, microservicios livianos o aplicaciones embebidas, sí puede serlo. **No es la única opción** (existe MicroProfile, Quarkus con Panache, etc.), pero es la dominante con diferencia.

## Testing de capa de persistencia

### Por qué importa

Los tests unitarios del dominio (Bloque 2) son fáciles: POJOs puros, sin dependencias externas. Los tests de la capa de persistencia, en cambio, **necesitan una base de datos** o algo que se le parezca. Y aquí hay decisiones importantes.

### Las opciones

**1. H2 en memoria.** Es lo que usamos en el curso. Rápido, sin configuración. Pero **no es la base de datos de producción**: dialecto distinto, funciones distintas, comportamiento sutilmente diferente. Útil para tests rápidos y de smoke; insuficiente si la query tiene cosas específicas del motor real.

**2. Testcontainers.** Levanta un contenedor Docker con la base de datos real (PostgreSQL, MySQL, lo que sea de producción) por test o por suite. Ralentiza arranque, pero los tests valen lo que un test de integración real. **Es lo que se usa en proyectos profesionales modernos**.

**3. Mockear el repositorio.** Aceptable para testear las capas superiores (servicio, controlador). Inaceptable para validar la propia query: estás testeando un mock, no la persistencia.

**4. `@DataJpaTest` (Spring Data).** Levanta un slice de Spring solo con JPA, transacción rollback al final del test, base embebida o configurable. La opción más práctica cuando se usa Spring Data.

### Qué se testea (y qué no)

Conviene tener claro:

- **El dominio** (POJOs) se testea sin base de datos.
- **El mapeo entidad → tabla** se testea con base de datos: persistir y leer, verificar que los datos están bien.
- **Las queries de repositorio** se testean con base de datos: que el JPQL produzca lo esperado.
- **El servicio** se testea mockeando el repositorio: que la lógica orqueste bien.

No probar las queries es uno de los errores más caros: una query mal pensada falla **el día que hay datos suficientes** para que falle.

## Migraciones de esquema

### El problema

Hibernate tiene una propiedad muy peligrosa que conviene desactivar cuanto antes:

```properties
hibernate.hbm2ddl.auto=update
```

Esto le dice a Hibernate que, al arrancar, **modifique el esquema** para que encaje con las entidades. Útil en desarrollo, **catastrófico en producción**: borra columnas, cambia tipos, pierde datos. Y lo hace en silencio.

La regla profesional: **el esquema lo gestiona una herramienta de migraciones, no Hibernate**.

### Las herramientas

**Flyway** y **Liquibase** son las dos referencias. Ambas hacen lo mismo en lo esencial:

- Versionan el esquema con scripts numerados (`V1__create_pizza.sql`, `V2__add_categoria_column.sql`).
- Al arrancar, comprueban qué scripts se han aplicado ya y ejecutan los pendientes en orden.
- Mantienen una tabla interna con el historial.

**Flyway** trabaja con SQL puro. Simple y explícito. **Liquibase** trabaja con XML/YAML/JSON (también admite SQL) y tiene más abstracciones (rollback declarativo, control de cambios estructurados). Para la mayoría de proyectos, Flyway es suficiente y más legible.

### Por qué importa para JPA

Porque cuando una migración añade una columna, tu entidad JPA debe declararla; cuando un campo desaparece de la entidad, hay que borrarlo del esquema. Las migraciones y las entidades **evolucionan en paralelo**, y la fuente de la verdad es el script de migración, no la anotación.

> Regla: **producción nunca confía en `hbm2ddl`**. Solo `validate` (compara) o `none` (ignora). El esquema lo construye Flyway/Liquibase.

## Alternativas modernas a JPA puro

JPA no es la única forma de persistir en Java moderno. Conocer las alternativas le da al alumno perspectiva y le permite elegir herramienta para cada proyecto.

### jOOQ

DSL Java que **modela SQL fielmente**. Generación de código a partir del esquema: el equipo tiene clases tipadas para tablas, columnas, funciones del motor concreto.

Filosofía radicalmente distinta a JPA: **no oculta SQL, lo abraza con tipos**. Brillante para proyectos donde la base de datos es el centro (data-heavy, reporting, lógica compleja en BD).

### Spring Data JDBC

Más reciente. Filosofía minimalista: una entidad por agregado, sin contexto de persistencia, sin lazy loading, sin dirty checking. Cada operación es explícita.

Para quien encuentra JPA demasiado mágico, Spring Data JDBC es la respuesta más sobria. Encaja muy bien con DDD precisamente porque **fuerza a pensar en agregados**.

### MyBatis

Mappers de SQL a objetos. El programador escribe el SQL; MyBatis lo asocia a métodos y mapea resultados. Sin ORM real: no hay sesiones, ni proxies, ni lazy loading.

Popular en empresas con tradición de SQL fuerte. Más explícito y menos "mágico" que JPA. Más verboso también.

### Hibernate Reactive / R2DBC

JPA es síncrono. Las plataformas reactivas (Project Reactor, RxJava) necesitan acceso a base de datos no bloqueante. **Hibernate Reactive** y **R2DBC** son las dos vías para conseguirlo. Cambian el modelo mental por completo: `Mono<Pizza>` en lugar de `Pizza`, composición funcional, manejo de backpressure.

Solo relevante si el resto del stack es reactivo. Para servicios síncronos tradicionales, complica sin aportar.

### NoSQL

Para algunos dominios (documentos sin esquema estable, datos jerárquicos enormes, alta tasa de escritura distribuida), una base relacional no es la mejor opción. MongoDB, Cassandra, DynamoDB tienen su sitio. **Spring Data tiene módulos para casi todos**: Spring Data MongoDB, Spring Data Cassandra, etc.

Mención importante: NoSQL **no es "lo siguiente" a JPA**. Es una herramienta para problemas distintos. Elegir entre relacional y NoSQL es una decisión arquitectónica que va mucho más allá de la persistencia.

## Una hoja de ruta razonable

Si Pedro quisiera proponer a sus alumnos una continuación natural tras este curso, este sería el orden:

1. **Spring Data JPA**: capitaliza inmediatamente lo aprendido aquí.
2. **Testing con Testcontainers**: cierra el ciclo de calidad.
3. **Flyway**: profesionaliza el manejo del esquema.
4. **Una alternativa a JPA** (jOOQ o Spring Data JDBC): da perspectiva.
5. **Performance tuning de Hibernate**: índices, cache de segundo nivel, fetch profiles, batch size. Vlad Mihalcea es la referencia obligada aquí.

Con esos cinco pasos completados, el alumno tiene un perfil muy sólido en persistencia Java.

## Cierre del curso

Hemos cerrado un círculo. Empezamos en JDBC a pelo, vimos por qué dolía, levantamos un ORM, modelamos un dominio rico, pasamos por las anotaciones, dominamos el contexto de persistencia, escribimos queries con criterio y enumeramos los errores que el alumno se va a encontrar.

Lo que cada alumno se lleva no es una lista de palabras clave: es **una forma de pensar la persistencia**. Pensar en agregados antes que en tablas, en consultas como decisiones antes que como sintaxis, en transacciones como compromisos antes que como código boilerplate, en el ORM como un contrato consciente antes que como una caja negra.

Si has llegado hasta aquí: enhorabuena. Acabas de aprender una de las capas más exigentes y más mal entendidas del backend Java.

A partir de aquí, todo lo que aprendas (Spring Data, reactivo, jOOQ, NoSQL, lo que sea) lo aprenderás sobre una base sólida.

Y eso es lo que importa.

## Resumen de la sección

- **Spring Data JPA** es la siguiente parada natural: automatiza repositorios sobre la base que ya conoces.
- **Testing con Testcontainers** y `@DataJpaTest` son el estándar profesional moderno.
