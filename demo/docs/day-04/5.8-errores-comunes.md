# 5.8 · Errores comunes: `LazyInitializationException`, N+1, ciclos en `toString`, transacción olvidada

## Por qué dedicar una sección entera a errores

Hibernate y JPA son herramientas que **funcionan bien** cuando se entienden, pero que producen errores **muy específicos** cuando no se entienden. La diferencia entre un programador júnior y uno con experiencia en JPA suele estar en haberse encontrado con estos cuatro errores y saber qué los causa de un vistazo.

Esta sección es deliberadamente práctica. Cada error: cómo se ve, qué lo causa, cómo se arregla, cómo se previene.

## Error 1: `LazyInitializationException`

### Cómo se ve

```
org.hibernate.LazyInitializationException: could not initialize proxy
[com.pizzeria.entity.PizzaEntity#42] - no Session
```

El alumno lo encontrará la primera vez al hacer algo como:

```java
public PizzaEntity buscarPizza(PizzaId id) {
    em.getTransaction().begin();
    PizzaEntity p = em.find(PizzaEntity.class, id);
    em.getTransaction().commit();
    em.close();
    return p;
}

// Más tarde, en otra capa:
PizzaEntity pizza = service.buscarPizza(id);
pizza.getIngredientes().size();   // ¡BOOM!
```

### Qué lo causa

Cuando una relación está marcada como `LAZY`, JPA no la carga al traer la entidad: en su lugar pone un **proxy**, un objeto que solo conoce su `id` y que tiene una referencia interna a la sesión que lo creó. La primera vez que tocamos un método del proxy, esa sesión se usa para cargar los datos de verdad.

El problema: si la sesión está **cerrada** o la transacción ha terminado, el proxy no tiene a quién pedirle los datos. Y lanza `LazyInitializationException`.

Es el coste de mover entidades fuera de la frontera transaccional.

### Cómo se arregla

Hay cuatro estrategias, ordenadas por preferencia:

**1. Cargar lo que necesitas dentro de la transacción.** Si en el caso de uso vas a usar los ingredientes, pídelos cuando aún hay sesión:

```java
PizzaEntity p = em.createQuery(
    "SELECT p FROM PizzaEntity p JOIN FETCH p.ingredientes WHERE p.id = :id",
    PizzaEntity.class
).setParameter("id", id).getSingleResult();
```

**2. Inicializar explícitamente antes de devolver.**

```java
PizzaEntity p = em.find(PizzaEntity.class, id);
Hibernate.initialize(p.getIngredientes()); // fuerza la carga
return p;
```

Funciona, pero requiere acordarte caso por caso. Frágil.

**3. Convertir a DTO dentro de la transacción.** Esta es la opción **arquitectónicamente más limpia**, y la que recomiendo en clase:

```java
PizzaEntity entidad = em.find(PizzaEntity.class, id);
return PizzaMapper.toDto(entidad); // mapper accede a ingredientes dentro de la sesión
```

El DTO sale de la capa de persistencia ya completo. Nadie fuera trata con proxies.

**4. Cambiar la relación a `EAGER`.** **No hacer esto.** Es el atajo que parece resolver el problema y que arruina el rendimiento de todas las consultas que no necesitaban esos datos. Si una relación está `EAGER`, **toda** consulta que toque esa entidad la trae cargada, aunque no la quieras.

### Cómo se previene

Regla clara:

> **Las entidades no salen del repositorio. Salen DTOs.**

Si el alumno asume esto desde el principio, `LazyInitializationException` casi desaparece de su vida.

## Error 2: N+1 (recordatorio + diagnóstico)

Ya lo vimos en 5.2, pero merece su sitio en el catálogo de errores comunes porque es **el más caro y el más invisible**.

### Cómo se ve

No se ve en una excepción. Se ve en el log de SQL:

```
SELECT * FROM comment WHERE pizza_id = 1;
SELECT * FROM pizza WHERE id = 1;
SELECT * FROM comment WHERE pizza_id = 2;
SELECT * FROM pizza WHERE id = 2;
SELECT * FROM comment WHERE pizza_id = 3;
SELECT * FROM pizza WHERE id = 3;
... (200 más)
```

O en la métrica de latencia: una página que debería tardar 50 ms tarda 3 segundos.

### Qué lo causa

Recorrer una colección de entidades y, para cada una, tocar una relación lazy:

```java
for (CommentEntity c : comments) {
    System.out.println(c.getPizza().getNombre()); // 1 query por iteración
}
```

### Cómo se arregla

`JOIN FETCH` en la consulta inicial (5.2):

```java
em.createQuery(
    "SELECT c FROM CommentEntity c JOIN FETCH c.pizza",
    CommentEntity.class
).getResultList();
```

### Cómo se previene

Dos cosas:

1. **Activar `hibernate.show_sql=true` en desarrollo.** Si ves una query en un bucle, hay N+1.
2. **Activar `hibernate.generate_statistics=true`** y mirar el `query count` por caso de uso. En tests de integración esto se puede automatizar.

## Error 3: ciclos en `toString` (y en `equals`/`hashCode`)

### Cómo se ve

```
java.lang.StackOverflowError
    at com.pizzeria.entity.PizzaEntity.toString(PizzaEntity.java:42)
    at com.pizzeria.entity.IngredienteEntity.toString(IngredienteEntity.java:31)
    at com.pizzeria.entity.PizzaEntity.toString(PizzaEntity.java:42)
    at com.pizzeria.entity.IngredienteEntity.toString(IngredienteEntity.java:31)
    ... (recursión infinita)
```

### Qué lo causa

Lombok. Casi siempre Lombok.

`@Data` o `@ToString` en una entidad con relación bidireccional genera un `toString()` que incluye **todos los campos**, incluyendo el lado inverso. `PizzaEntity.toString()` imprime sus ingredientes; cada `IngredienteEntity.toString()` imprime su pizza; cada pizza imprime sus ingredientes... y así hasta que la pila se desborda.

Lo mismo pasa con `@EqualsAndHashCode` si compara colecciones que apuntan al lado inverso.

### Cómo se arregla

**No usar Lombok `@Data` en entidades JPA.** Si se usa Lombok, hacerlo selectivo:

```java
@Entity
@Getter
@Setter
@NoArgsConstructor
public class PizzaEntity {
    @Id
    private Long id;
    
    @ManyToMany
    @ToString.Exclude  // <-- evita el ciclo
    @EqualsAndHashCode.Exclude
    private Set<IngredienteEntity> ingredientes;
}
```

Pero la recomendación más sana es **escribir el `toString` a mano** y limitarlo a campos primitivos:

```java
@Override
public String toString() {
    return "PizzaEntity{id=" + id + ", nombre=" + nombre + "}";
}
```

### Cómo se previene

Regla:

> **`toString`, `equals` y `hashCode` en entidades nunca tocan relaciones**.

Esto se acentúa por otro motivo, esta vez de diseño: en 2.4 vimos que la identidad de fila es por `id`. `equals` y `hashCode` deben usar **el id** y nada más. Y mejor todavía, deben tener en cuenta que el id puede ser `null` antes del `persist`. Hay artículos clásicos (Vlad Mihalcea, por ejemplo) que tratan esto en detalle; en clase basta con decir: **identidad por id, comparación cuidadosa con null**.

## Error 4: la transacción olvidada

### Cómo se ve

A veces como excepción:

```
javax.persistence.TransactionRequiredException: 
Executing an update/delete query
```

O peor, en silencio:

```java
em.persist(pizza); // aparentemente OK
em.close();
// ¡No se guardó nada! No había transacción.
```

### Qué lo causa

En JPA puro (sin Spring), **todas las operaciones de escritura necesitan transacción activa**. Y todas las operaciones que necesitan flush también. Sin `em.getTransaction().begin()` y `commit()`, `persist` no falla ruidosamente: el cambio simplemente no se aplica al cerrar.

```java
em.persist(pizza); // se acumula en el contexto, pero el contexto se descarta al cerrar
em.close();
```

Es uno de los errores más frustrantes para el principiante porque **no hay excepción**: el programa parece correcto, pero la base de datos sigue vacía.

### Cómo se arregla

El patrón canónico:

```java
EntityManager em = emf.createEntityManager();
EntityTransaction tx = em.getTransaction();

try {
    tx.begin();
    // operaciones
    em.persist(pizza);
    tx.commit();
} catch (RuntimeException e) {
    if (tx.isActive()) tx.rollback();
    throw e;
} finally {
    em.close();
}
```

Es verboso. Por eso en proyectos reales esto **se delega** a Spring (`@Transactional`), a un framework de capa, o a un helper propio. Pero conocer el patrón a pelo es esencial: lo que `@Transactional` esconde es exactamente este try-catch-finally.

### Cómo se previene

- Cuando aparezca un código "que persiste pero no guarda", lo primero a revisar es la transacción.
- Cuando se vea `TransactionRequiredException`, la respuesta no es "voy a probar a cambiar el query", es "me he olvidado del `begin()`".

## Un quinto error frecuente: `OptimisticLockException`

Lo menciono brevemente porque aparecerá cuando trabajen con cargas concurrentes. Si la entidad tiene `@Version`, JPA detecta que dos usuarios actualizaron al mismo registro a la vez y lanza:

```
javax.persistence.OptimisticLockException
```

La solución no es ignorarlo: es **recuperar la entidad, mostrar al usuario los cambios actuales y dejar que decida qué hacer**. Pero el detalle de concurrency control queda fuera del curso. Mencionarlo y nombrar `@Version` es suficiente.

## Una pista de oro para depurar

Para todos estos errores, hay un consejo común que vale la pena interiorizar:

> **Activa el log SQL de Hibernate desde el día 1.**

`hibernate.show_sql=true`, `hibernate.format_sql=true`, `hibernate.use_sql_comments=true`. Con eso, las queries reales que está lanzando el motor están delante tuyo. El 80% de los problemas se resuelven leyéndolas con calma.

## Resumen de la sección

- **`LazyInitializationException`**: relación lazy tocada fuera de la sesión. Solución: cargar dentro o devolver DTOs.
- **N+1**: bucle que toca relación lazy. Solución: `JOIN FETCH`. Prevención: log SQL en desarrollo.
- **Ciclos en `toString`**: relaciones bidireccionales con Lombok `@Data`. Solución: excluir relaciones de `toString`/`equals`.
- **Transacción olvidada**: persistencias silenciosas o `TransactionRequiredException`. Solución: patrón `begin()/commit()/rollback()/close()`.
- **`OptimisticLockException`**: concurrencia con `@Version`. Mención y se deja como tema avanzado.
- **El log SQL es el primer aliado al depurar.**
