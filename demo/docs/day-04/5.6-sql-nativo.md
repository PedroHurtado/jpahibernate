# 5.6 · SQL nativo: `createNativeQuery`, mapeo a entidades y a DTOs

## Cuándo está bien bajarse del ORM

Llevamos cinco secciones diciendo que el ORM existe para no escribir SQL. Y es cierto. Pero también es cierto que **hay queries que JPQL simplemente no puede expresar**, o que las expresa mucho peor que SQL puro:

- **Window functions** (`ROW_NUMBER() OVER (...)`, `RANK()`, `LEAD/LAG`).
- **CTEs recursivas** (`WITH RECURSIVE ...`) para árboles jerárquicos.
- **Vistas materializadas** y consultas que las explotan.
- **Funciones específicas del dialecto** (`STRING_AGG` en PostgreSQL, `JSON_TABLE` en MySQL, geoespaciales con PostGIS).
- **Optimizaciones quirúrgicas** donde necesitas dictar al planificador qué índice usar o cómo ordenar los joins.

Para esto JPA ofrece `createNativeQuery`: una puerta de salida controlada del modelo de entidades hacia SQL puro.

## La forma básica

```java
List<Object[]> filas = em.createNativeQuery(
    "SELECT id, nombre FROM pizza WHERE precio > ?"
).setParameter(1, new BigDecimal("12")).getResultList();

for (Object[] fila : filas) {
    Long id = ((Number) fila[0]).longValue();
    String nombre = (String) fila[1];
}
```

Lo primero que llama la atención: el SQL es **directo a la BD**. `pizza` es el nombre de la **tabla**, no de la entidad. `precio` es el nombre de la **columna**, no del atributo. El proveedor JPA no interpreta nada: lo envía tal cual.

Las consecuencias:

- **Pierdes portabilidad.** Esa query funcionará en H2 y en PostgreSQL, pero `STRING_AGG` solo en Postgres y `LISTAGG` solo en Oracle.
- **No hay refactor automático.** Si renombras la tabla `pizza` a `pizzas`, JPA no se entera. La query revienta en runtime.
- **Los parámetros son posicionales por defecto.** Los nombrados (`:nombre`) también funcionan en native query, pero el dialecto a veces complica las cosas. Lo recomendable es usar posicionales en native y nombrados en JPQL.
- **Resultado por defecto: `Object[]`** o (`List<Object[]>`). Sin tipado. Hay que castear cada columna.

Ese último punto es el que duele más. Native query crudo es como volver a JDBC pero sin las ventajas de control fino. Por eso existen las dos variantes que vienen ahora.

## Mapeo a entidad: native query que devuelve entidades gestionadas

Si la query devuelve filas que **coinciden estructuralmente con una entidad**, podemos pedirle a JPA que las mapee automáticamente:

```java
List<PizzaEntity> pizzas = em.createNativeQuery(
    "SELECT * FROM pizza WHERE precio > ?",
    PizzaEntity.class
).setParameter(1, new BigDecimal("12")).getResultList();
```

Pasamos `PizzaEntity.class` como segundo argumento. JPA usa el mapping de la entidad para reconstruir objetos. Esos objetos **entran al contexto de persistencia** como si vinieran de un `find` o de un `SELECT` JPQL. Aplica `dirty checking`, cascadas, todo.

Condición práctica: el `SELECT` tiene que devolver todas las columnas que la entidad espera. `SELECT id, nombre FROM pizza` con `PizzaEntity.class` falla si la entidad mapea también `precio`, porque JPA no encuentra esa columna en el resultado.

`SELECT *` es la opción más segura cuando el mapeo es directo, aunque pueda hacer ruido en code reviews.

## Mapeo a DTO: el caso útil de verdad

Native query suele aparecer para **informes y vistas agregadas**, donde el resultado no encaja en ninguna entidad. Por ejemplo: ranking de las 5 pizzas con más comentarios.

```sql
SELECT p.nombre AS nombre, COUNT(c.id) AS total
FROM pizza p
LEFT JOIN comment c ON c.pizza_id = p.id
GROUP BY p.nombre
ORDER BY total DESC
LIMIT 5
```

Esto no es una entidad. Es un **DTO de reporting**: dos campos, `nombre` y `total`. Para mapearlo hay dos caminos.

### Opción A: `@SqlResultSetMapping`

Es el mecanismo "oficial" de JPA. Se declara el mapeo en una anotación (típicamente sobre alguna entidad o en `package-info`) y se referencia por nombre:

```java
@SqlResultSetMapping(
    name = "RankingPizzaMapping",
    classes = @ConstructorResult(
        targetClass = RankingPizzaDto.class,
        columns = {
            @ColumnResult(name = "nombre", type = String.class),
            @ColumnResult(name = "total", type = Long.class)
        }
    )
)
@Entity
public class PizzaEntity { ... }
```

```java
public record RankingPizzaDto(String nombre, Long total) {}
```

```java
List<RankingPizzaDto> ranking = em.createNativeQuery(
    "SELECT p.nombre AS nombre, COUNT(c.id) AS total " +
    "FROM pizza p LEFT JOIN comment c ON c.pizza_id = p.id " +
    "GROUP BY p.nombre ORDER BY total DESC LIMIT 5",
    "RankingPizzaMapping"
).getResultList();
```

Funciona y es la solución portable que respeta la especificación. Pero es **verbosa** y acopla la entidad a una anotación que tiene poco que ver con ella.

### Opción B (recomendada): proyección manual

Honestamente, lo más práctico es ejecutar el native query, recibir `Object[]` y mapear a mano:

```java
@SuppressWarnings("unchecked")
List<Object[]> filas = em.createNativeQuery(
    "SELECT p.nombre, COUNT(c.id) " +
    "FROM pizza p LEFT JOIN comment c ON c.pizza_id = p.id " +
    "GROUP BY p.nombre ORDER BY 2 DESC LIMIT 5"
).getResultList();

List<RankingPizzaDto> ranking = filas.stream()
    .map(f -> new RankingPizzaDto(
        (String) f[0],
        ((Number) f[1]).longValue()
    ))
    .toList();
```

Menos elegante en apariencia, pero **explícito** y sin acoplar la entidad a la query. Para queries de reporting puntuales suele ganar.

> **Decisión de curso:** mostrar las dos opciones, decir cuál se usa en proyectos modernos (proyección manual o, ya con Spring Data, projection interfaces) y dejar `@SqlResultSetMapping` documentada como la forma estándar.

## El detalle del `@NamedNativeQuery`

Igual que JPQL tiene `@NamedQuery`, native tiene `@NamedNativeQuery`. Se declara en la entidad y se invoca con `em.createNamedQuery("nombre")`. Mismo trade-off: centraliza la query en un sitio, pero la mete dentro de una anotación de la entidad. En proyectos donde las queries crecen, suele preferirse mantenerlas como constantes en clases utilitarias o en repositorios. No vamos a profundizar.

## Lo que no se debe hacer con native

Tres antipatrones comunes que conviene marcar en clase:

**1. CRUD básico con native.** "Como yo SQL me sé, voy a hacer `INSERT INTO pizza VALUES ...` con native." Esto rompe todo el contexto de persistencia. La entidad no queda gestionada, los callbacks no se disparan, dirty checking no funciona. Para CRUD, JPA. Para informes, native.

**2. `WHERE id IN (...)` construyendo el `(...)` con concatenación.** Inyección SQL directa. `setParameter` con una `Collection` funciona perfectamente en native query desde JPA 2.1; no hay excusa para concatenar.

**3. Olvidar que native esquiva el contexto.** Si haces un `UPDATE pizza SET precio = 0` por native, las pizzas cargadas en memoria siguen con su precio anterior. Es exactamente la misma trampa que con `UPDATE` JPQL masivo (5.3), pero en native es aún más fácil caer.

## Cuándo cada cosa: la regla práctica

Tras todo el capítulo de consultas, la regla de oro:

| Necesidad | Herramienta |
|---|---|
| CRUD básico | `EntityManager` (`find`, `persist`, `merge`) |
| Consulta sencilla y portable | **JPQL** + `TypedQuery` |
| Consulta con muchos filtros opcionales | Criteria (o Specifications, si Spring Data) |
| Reportes, agregaciones, window functions | **SQL nativo** + DTO |
| Optimización quirúrgica (hints, índices forzados) | **SQL nativo** |

Es la tabla que conviene asentar antes de pasar a la siguiente sección.

## Resumen de la sección

- **`createNativeQuery`** envía SQL puro al motor; útil cuando JPQL se queda corto.
- Sin mapeo, devuelve `Object[]`; con `Class<T>` mapea a entidad gestionada; con `@SqlResultSetMapping` mapea a DTOs.
- Para reporting, **proyección manual a DTO** suele ser lo más práctico.
- Native **rompe portabilidad** y **no protege el contexto**: usar con criterio.
- Antipatrones: CRUD con native, inyección por concatenación, ignorar la desincronización.
