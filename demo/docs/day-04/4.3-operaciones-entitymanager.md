# 4.3. Operaciones: `persist`, `merge`, `find`, `remove`, `flush`, `refresh`, `detach`, `clear`

> **Duración estimada:** 25 min (10 min teoría + 15 min práctica)

---

## 🧠 Teoría rápida (10 min)

Ya tenemos el modelo de estados de **4.2**. Ahora vamos a recorrer las operaciones que provocan las transiciones entre esos estados. Cada una responde a una pregunta concreta.

### `persist(entidad)` — "esto es nuevo, ocúpate"

Pasa una entidad de `transient` a `managed`. Le asigna id (si toca generarlo) y la mete en el contexto. Hasta el próximo `flush` no se ejecuta el `INSERT`, pero el id ya está disponible (con estrategias de generación que lo permitan).

> **No usar con entidades que ya tienen id en BD.** Si pasas una entidad detached a `persist`, vas a romper algo. Para detached existe `merge`.

### `merge(entidad)` — "esto puede ser nuevo o no, normalízalo"

Toma una entidad (típicamente detached) y devuelve **una nueva instancia managed** con los datos copiados. Como vimos en **4.2**, la trampa es que **no reattacha la original**: la copia. Por eso siempre se hace `entidad = em.merge(entidad)`.

> En la práctica, si tu arquitectura tiene mappers y repositories como la nuestra, `merge` aparece poco. Lo necesitas cuando recibes una entidad desde "fuera" (un DTO ya mapeado en otra sesión, por ejemplo) y quieres meterla al contexto. En código limpio con dominio + repository, casi siempre eliges entre `persist` (entidad nueva) y `find` + modificación (entidad existente).

### `find(Clase.class, id)` — "tráeme esta y vigílala"

Busca por id, devuelve la entidad **managed**. Si ya estaba en el contexto, devuelve la misma instancia (sin tocar la BD). Si no, hace `SELECT`, la mete en el contexto, la devuelve.

> Devuelve `null` si no existe. La alternativa es `getReference(Clase.class, id)`, que devuelve un **proxy** y solo va a BD cuando le pides un atributo. Útil para asociaciones por id, no para uso general.

### `remove(entidad)` — "esto se borra"

Marca la entidad como `removed`. El `DELETE` se ejecuta en el próximo `flush`. La entidad debe estar `managed` (si está `detached` te lanza excepción; primero `merge`, luego `remove`).

### `flush()` — "sincroniza ya"

Fuerza a Hibernate a ejecutar el SQL pendiente (los `INSERT`, `UPDATE`, `DELETE` acumulados) **sin cerrar la transacción**. Es decir: los cambios van a la BD pero todavía pueden hacerse `rollback`.

> Útil para ver el SQL en orden, para refrescar una query justo después de un cambio, o para forzar errores de constraint antes del commit. **Llamarlo a saco "por si acaso" es síntoma de no entender el modelo.**

### `refresh(entidad)` — "tira lo que tengas, lee de BD"

Sobreescribe la entidad managed con los datos actuales de la BD. Pierdes cualquier cambio en memoria. Útil cuando sospechas que alguien (otro proceso, un trigger) ha modificado la fila por debajo.

### `detach(entidad)` — "deja de vigilar esta"

Saca la entidad del contexto. Pasa de `managed` a `detached`. Los cambios posteriores ya no se sincronizan.

### `clear()` — "olvídalo todo"

Vacía el contexto entero. Todas las entidades pasan a `detached`. Útil tras un proceso masivo para liberar memoria, o cuando quieres re-leer de BD desde cero.

### Tabla resumen

| Operación   | Origen        | Destino       | SQL ejecutado en              |
|-------------|---------------|---------------|-------------------------------|
| `persist`   | transient     | managed       | flush / commit                |
| `merge`     | detached      | managed (otra)| flush / commit                |
| `find`      | (BD)          | managed       | inmediato (si no estaba)      |
| `remove`    | managed       | removed       | flush / commit                |
| `flush`     | —             | —             | ahora mismo                   |
| `refresh`   | managed       | managed       | inmediato (SELECT)            |
| `detach`    | managed       | detached      | —                             |
| `clear`     | (todo) managed| (todo) detached| —                            |

## 🛠️ Práctica guiada (15 min)

### Paso 1 — Demo de `find` con caché de primer nivel

Crea `com.pizzeria.sandbox.OperacionesDemo`:

```java
package com.pizzeria.sandbox;

import com.pizzeria.infrastructure.JpaBootstrap;
import com.pizzeria.persistence.ingrediente.IngredienteJpa;
import jakarta.persistence.EntityManager;

import java.math.BigDecimal;

public class OperacionesDemo {

    public static void main(String[] args) {
        try {
            demoFindCachea();
            demoFlushVsCommit();
            demoRefresh();
            demoDetachClear();
        } finally {
            JpaBootstrap.shutdown();
        }
    }

    static void demoFindCachea() {
        System.out.println("\n=== find() cachea en el contexto ===");
        EntityManager em = JpaBootstrap.openEntityManager();
        em.getTransaction().begin();

        IngredienteJpa nuevo = new IngredienteJpa();
        nuevo.setNombre("Tomate");
        nuevo.setCoste(new BigDecimal("0.80"));
        em.persist(nuevo);
        em.getTransaction().commit();

        Long id = nuevo.getId();

        em.getTransaction().begin();
        System.out.println("Primer find:");
        IngredienteJpa a = em.find(IngredienteJpa.class, id);
        System.out.println("Segundo find (NO debe disparar SELECT):");
        IngredienteJpa b = em.find(IngredienteJpa.class, id);
        System.out.println("¿misma instancia? " + (a == b));
        em.getTransaction().commit();
        em.close();
    }
}
```

Observa la salida con `show_sql=true`: el segundo `find` **no genera `SELECT`**. La entidad ya estaba `managed`.

### Paso 2 — `flush` vs `commit`

Añade este método:

```java
static void demoFlushVsCommit() {
    System.out.println("\n=== flush adelanta el SQL ===");
    EntityManager em = JpaBootstrap.openEntityManager();
    em.getTransaction().begin();

    IngredienteJpa ing = new IngredienteJpa();
    ing.setNombre("Aceitunas");
    ing.setCoste(new BigDecimal("0.60"));

    System.out.println("Antes de persist (sin SQL):");
    em.persist(ing);
    System.out.println("Después de persist (sin SQL todavía):");
    em.flush();
    System.out.println("Después de flush (INSERT ya ejecutado):");
    em.getTransaction().commit();
    System.out.println("Después de commit (la transacción se cierra):");
    em.close();
}
```

Comprueba que el `INSERT` aparece en `flush`, no en `persist`. El `commit` solo cierra la transacción.

### Paso 3 — `refresh` recupera del disco

```java
static void demoRefresh() {
    System.out.println("\n=== refresh descarta cambios en memoria ===");
    EntityManager em = JpaBootstrap.openEntityManager();
    em.getTransaction().begin();

    IngredienteJpa ing = new IngredienteJpa();
    ing.setNombre("Pepperoni");
    ing.setCoste(new BigDecimal("1.50"));
    em.persist(ing);
    em.flush();

    ing.setCoste(new BigDecimal("99.99"));  // cambio en memoria
    System.out.println("Coste antes de refresh: " + ing.getCoste());

    em.refresh(ing);  // se descarta y se relee
    System.out.println("Coste después de refresh: " + ing.getCoste());

    em.getTransaction().rollback();
    em.close();
}
```

Salida esperada:

```
Coste antes de refresh: 99.99
Coste después de refresh: 1.50
```

### Paso 4 — `detach` y `clear`

```java
static void demoDetachClear() {
    System.out.println("\n=== detach y clear ===");
    EntityManager em = JpaBootstrap.openEntityManager();
    em.getTransaction().begin();

    IngredienteJpa a = new IngredienteJpa();
    a.setNombre("Cebolla");
    a.setCoste(new BigDecimal("0.30"));
    em.persist(a);

    IngredienteJpa b = new IngredienteJpa();
    b.setNombre("Champiñón");
    b.setCoste(new BigDecimal("0.50"));
    em.persist(b);

    System.out.println("¿a managed? " + em.contains(a) + " | ¿b managed? " + em.contains(b));

    em.detach(a);
    System.out.println("Tras detach(a):");
    System.out.println("¿a managed? " + em.contains(a) + " | ¿b managed? " + em.contains(b));

    em.clear();
    System.out.println("Tras clear():");
    System.out.println("¿a managed? " + em.contains(a) + " | ¿b managed? " + em.contains(b));

    em.getTransaction().rollback();
    em.close();
}
```

Observa: `detach` saca uno solo; `clear` los saca a todos.

### Paso 5 — Mini-reto: ¿qué hace este código?

Antes de ejecutarlo, **predice la salida**:

```java
EntityManager em = JpaBootstrap.openEntityManager();
em.getTransaction().begin();

IngredienteJpa ing = new IngredienteJpa();
ing.setNombre("Bacon");
ing.setCoste(new BigDecimal("1.80"));
em.persist(ing);

em.detach(ing);
ing.setCoste(new BigDecimal("2.50"));

em.getTransaction().commit();
em.close();

// ¿Se guardó el "Bacon"? ¿Con qué coste?
```

> *Respuesta:* **Sí se guardó, con coste `1.80`.**
> El `persist` programó el `INSERT`. El `detach` lo sacó del contexto, pero el `INSERT` ya estaba en la cola de la transacción. El cambio posterior a `2.50` no se aplicó porque la entidad ya no estaba `managed`.
> Esta es exactamente la clase de comportamiento contraintuitivo que justifica entender bien el modelo de estados.

## 🎯 Cierre

Estas ocho operaciones son **todo el repertorio** que necesitas para CRUD con JPA. El resto son detalles. La sección **4.4** se centra en algo que ha aparecido implícito en toda la práctica: el **dirty checking**, esa "magia" que detecta cambios sin llamadas explícitas.

> **Idea para llevarse:** `persist` no es `INSERT`, `remove` no es `DELETE`. Son operaciones sobre el contexto. El SQL llega después, cuando JPA decide.
