# 5.4 · Criteria API: para qué existe y por qué duele

## El problema que JPQL en `String` no resuelve

JPQL es legible, expresivo y suficiente para el 90% de las consultas. Pero tiene una limitación importante: **es un `String`**. Y en cuanto la consulta deja de ser fija y empieza a depender de filtros opcionales, los `String` se vuelven un problema.

El caso típico: un formulario de búsqueda de pizzas. El usuario puede filtrar (o no) por nombre, por rango de precio, por ingrediente. Las combinaciones son 2³ = 8. Si lo resolvemos con JPQL en `String`:

```java
StringBuilder jpql = new StringBuilder("SELECT p FROM PizzaEntity p WHERE 1=1");
Map<String, Object> params = new HashMap<>();

if (nombre != null) {
    jpql.append(" AND p.nombre LIKE :nombre");
    params.put("nombre", "%" + nombre + "%");
}
if (precioMin != null) {
    jpql.append(" AND ...");
    params.put("precioMin", precioMin);
}
// ...

TypedQuery<PizzaEntity> q = em.createQuery(jpql.toString(), PizzaEntity.class);
params.forEach(q::setParameter);
```

Funciona. Pero es horrible: trozos de SQL en variables, `WHERE 1=1` como truco para concatenar, ningún chequeo en tiempo de compilación, errores de sintaxis que solo aparecen al ejecutar. Cualquier cambio en `PizzaEntity` (renombrar `nombre` a `denominacion`, por ejemplo) no rompe nada hasta que el test corre, o peor, hasta que el usuario hace la búsqueda.

JPA, consciente de esto, ofrece una alternativa: **Criteria API**.

## Qué es Criteria API

Criteria API es una API **tipada y programática** para construir consultas. En lugar de escribir un `String`, se compone la query con objetos Java:

```java
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<PizzaEntity> cq = cb.createQuery(PizzaEntity.class);
Root<PizzaEntity> p = cq.from(PizzaEntity.class);
cq.select(p);

List<Predicate> predicados = new ArrayList<>();
if (nombre != null) {
    predicados.add(cb.like(p.get("nombre"), "%" + nombre + "%"));
}
if (precioMin != null) {
    // ... otro predicado
}

cq.where(predicados.toArray(new Predicate[0]));

List<PizzaEntity> resultado = em.createQuery(cq).getResultList();
```

Lo que ganamos respecto al `StringBuilder`:

- **Composición programática limpia.** Los predicados son objetos, se acumulan en una lista, no hay concatenación de strings.
- **Inyección imposible**: no hay literales en la query.
- **Estructura clara**: `Root`, `Predicate`, `Order`, `Selection` son piezas explícitas.

Pero también tenemos un coste evidente: **es muchísimo más verbosa**. Una query JPQL de una línea son cinco o seis líneas en Criteria.

## El detalle que causa el dolor: los strings de atributo

En el ejemplo anterior usamos `p.get("nombre")`. Ese `"nombre"` es un `String`. Si renombramos el atributo en la entidad, el compilador no se entera. **Acabamos de perder la principal ventaja prometida**: el chequeo en tiempo de compilación.

JPA conoce este problema y propone una solución: el **Metamodel estático**. Es una clase generada (`PizzaEntity_`) con campos estáticos tipados:

```java
predicados.add(cb.like(p.get(PizzaEntity_.nombre), "%" + nombre + "%"));
```

Ahora sí: si `PizzaEntity` cambia, `PizzaEntity_` se regenera y la compilación falla en el sitio correcto.

El problema: hay que **configurar un anotation processor** (típicamente `hibernate-jpamodelgen`) en el `pom.xml` para que esas clases se generen. Es viable, pero añade complejidad de build y muchos equipos no lo hacen. El resultado: Criteria con strings, que es lo peor de los dos mundos.

## Comparativa honesta

Tomemos la query de pizzas con precio mayor que 12 €, ordenadas por nombre. Veamos las dos versiones lado a lado.

**JPQL:**

```java
List<PizzaEntity> resultado = em.createQuery(
    "SELECT p FROM PizzaEntity p WHERE p.precio.cantidad > :limite ORDER BY p.nombre",
    PizzaEntity.class
).setParameter("limite", new BigDecimal("12")).getResultList();
```

**Criteria:**

```java
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<PizzaEntity> cq = cb.createQuery(PizzaEntity.class);
Root<PizzaEntity> p = cq.from(PizzaEntity.class);

cq.select(p)
  .where(cb.greaterThan(p.get("precio").get("cantidad"), new BigDecimal("12")))
  .orderBy(cb.asc(p.get("nombre")));

List<PizzaEntity> resultado = em.createQuery(cq).getResultList();
```

Para una query fija como esta, Criteria es claramente peor: más código, menos legible. Solo merece la pena cuando **la consulta cambia en función de parámetros**.

## Cuándo usar Criteria de verdad

La regla pragmática que recomiendo asentar en clase:

> **Criteria API solo se justifica cuando la query es dinámica.** Si tiene una forma fija, JPQL. Siempre.

Casos donde Criteria realmente brilla:

1. **Buscadores con filtros opcionales** (el ejemplo del principio).
2. **Construcción de queries a partir de DSLs internos**: por ejemplo, una capa que recibe un objeto de tipo "criterio de búsqueda" y lo traduce a una query.
3. **Composición reutilizable**: tener métodos que devuelven `Predicate` y combinarlos (`cb.and(...)`, `cb.or(...)`) sin recurrir a concatenar strings.

Para cualquier otra cosa, JPQL es más corto, más rápido de escribir y más fácil de mantener.

## El otro coste oculto

Hay otra razón por la que Criteria duele en proyectos reales: **es más difícil de leer rápido**. JPQL se parece a SQL, y cualquier programador sabe leer SQL. Criteria es un DSL Java específico que requiere recordar `cb.like`, `cb.greaterThan`, `cb.asc`, `Root`, `Selection`... La curva de entrada es real y la productividad cae.

En equipos con rotación, donde la query la va a mantener alguien que no la escribió, JPQL gana por goleada. Criteria se vuelve útil cuando hay **una sola persona o equipo experto** manteniéndolo, o cuando la dinamicidad lo hace imprescindible.

## El verdadero motivo de existir

Conviene ser honesto en el aula: Criteria API se introdujo en JPA 2.0 (año 2009) como respuesta a un problema real (queries dinámicas seguras y tipadas). La solución que escogió la especificación es **fea**. Hay alternativas mucho más ergonómicas que han ido apareciendo: Spring Data JPA Specifications (que veremos brevemente en 5.5), QueryDSL (un DSL externo muy popular hace unos años), Blaze-Persistence, jOOQ.

Criteria API sigue existiendo porque es **estándar**. Está en la especificación. No depende de librerías externas. Pero la realidad de los proyectos modernos es que se evita siempre que se puede.

## Notas didácticas para Pedro

Mi recomendación de cómo enfocar esta sección en clase, tres movimientos:

1. **Mostrar el problema** con `StringBuilder` y JPQL concatenado. Que duela.
2. **Mostrar Criteria** como la respuesta de la especificación. Que duela también, pero de otra forma.
3. **Cerrar con la regla**: dinámico → Criteria; fijo → JPQL; en proyectos reales, miramos alternativas.

No conviene profundizar mucho más en el API (Joins en Criteria, subqueries, etc.) porque es tiempo invertido en una herramienta que vamos a recomendar evitar. Mejor dejar claro qué es, por qué existe, cuándo aparece y pasar a algo más útil.

## Resumen de la sección

- **Criteria API** existe para escribir queries **dinámicas** de forma tipada y segura.
- Es **verbosa**: para queries fijas, JPQL es muy superior.
- Los strings de atributo (`p.get("nombre")`) cancelan la promesa de tipado salvo que se configure el **metamodel estático** (`hibernate-jpamodelgen`).
- La regla: **dinámico → Criteria; fijo → JPQL**.
- En la práctica, alternativas modernas (Specifications, QueryDSL) suelen preferirse cuando hay libertad de stack.

En 5.5 vemos por encima qué son las Specifications de Spring Data y por qué resuelven mejor el problema.
