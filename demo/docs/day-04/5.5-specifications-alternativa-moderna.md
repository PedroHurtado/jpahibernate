# 5.5 · Mención a Specifications como alternativa moderna

## Por qué meter esto en un curso de JPA puro

Esta sección es deliberadamente breve. Specifications **no son parte de JPA**: pertenecen a Spring Data JPA. Y el curso es JPA sin Spring. ¿Qué hacen aquí entonces?

Por dos motivos:

1. **El alumno va a encontrarlas en cualquier proyecto real.** La proporción de empresas que usan JPA sin Spring es minoritaria. Salir del curso sin saber qué son Specifications cuando aparezcan en el primer proyecto es dejar un agujero.
2. **Cierran un círculo conceptual abierto en 5.4.** Dijimos que Criteria es la solución estándar a las queries dinámicas, y que duele. Specifications es la respuesta ergonómica al mismo problema. Mostrarlas ayuda a entender por qué la industria evita Criteria directo.

## La idea en una frase

Una `Specification<T>` es **un predicado reutilizable y combinable** construido sobre Criteria, que se aplica a una consulta.

En código:

```java
// Una Specification expresa "qué pizzas cumplen esta condición"
Specification<PizzaEntity> precioMayorQue = (root, query, cb) ->
    cb.greaterThan(root.get("precio").get("cantidad"), new BigDecimal("12"));

Specification<PizzaEntity> nombreContiene = (root, query, cb) ->
    cb.like(root.get("nombre"), "%" + filtro + "%");

// Y se combinan con operadores
Specification<PizzaEntity> combinada = precioMayorQue.and(nombreContiene);

// Spring Data las ejecuta
List<PizzaEntity> resultado = pizzaRepository.findAll(combinada);
```

Lo importante para el alumno no es la sintaxis exacta: es **la idea de composición**. En lugar de tener una query con todos los `if (filtro != null) { ... }`, descomponemos en piezas pequeñas y las combinamos.

## Comparativa lado a lado

Para el caso del buscador de pizzas con filtros opcionales (nombre, precio mínimo, ingrediente):

**Criteria API "a pelo":**

```java
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<PizzaEntity> cq = cb.createQuery(PizzaEntity.class);
Root<PizzaEntity> p = cq.from(PizzaEntity.class);

List<Predicate> ps = new ArrayList<>();
if (nombre != null) ps.add(cb.like(p.get("nombre"), "%" + nombre + "%"));
if (precioMin != null) ps.add(cb.greaterThan(p.get("precio").get("cantidad"), precioMin));
if (ingrediente != null) {
    Join<PizzaEntity, IngredienteEntity> join = p.join("ingredientes");
    ps.add(cb.equal(join.get("nombre"), ingrediente));
}

cq.select(p).where(ps.toArray(new Predicate[0]));
List<PizzaEntity> resultado = em.createQuery(cq).getResultList();
```

**Specifications:**

```java
Specification<PizzaEntity> spec = Specification.where(null);

if (nombre != null) spec = spec.and(PizzaSpecs.nombreContiene(nombre));
if (precioMin != null) spec = spec.and(PizzaSpecs.precioMayorQue(precioMin));
if (ingrediente != null) spec = spec.and(PizzaSpecs.tieneIngrediente(ingrediente));

List<PizzaEntity> resultado = pizzaRepository.findAll(spec);
```

Con cada `Spec` definida una sola vez en una clase utilitaria (`PizzaSpecs`), reutilizable en mil sitios. El código del caso de uso queda declarativo: "filtra por nombre, si lo hay; por precio, si lo hay; por ingrediente, si lo hay".

Esta es la ergonomía que falta en Criteria puro. Es Criteria por debajo, pero envuelto en una abstracción que **separa la construcción de los predicados de su composición**.

## Qué necesita el alumno saber

Para los efectos de este curso, basta con que el alumno se quede con cuatro cosas:

1. **Specifications es Spring Data, no JPA**. Si tu proyecto no usa Spring, no las tienes.
2. **Resuelven el mismo problema que Criteria**: queries dinámicas tipadas.
3. **Lo hacen mejor**: predicados reutilizables y combinables.
4. **Internamente usan Criteria**. No son magia ni un competidor: son una capa ergonómica encima.

Hay otras alternativas también: **QueryDSL** (DSL externo basado en generación de código, muy popular hace una década), **jOOQ** (más orientado a SQL puro con tipado fuerte), **Blaze-Persistence** (extensiones avanzadas sobre Criteria). Cada una tiene su nicho. Mencionarlas brevemente sirve para que el alumno sepa que existen y para que entienda que **la comunidad lleva 15 años buscando alternativas a Criteria**: si te resulta incómoda, no es tu fallo, es generalizado.

## Por qué no entramos a fondo

Tres razones honestas para Pedro:

1. **No es JPA estándar.** El curso es de JPA puro; meter Specifications con detalle es romper el contrato.
2. **Requiere Spring Data**, que es un universo en sí mismo.
3. **El tiempo del curso es limitado** y se gasta mejor reforzando JPQL, `JOIN FETCH` y el manejo correcto del contexto de persistencia, que son la base sobre la que cualquier solución (Spring Data, Specifications, QueryDSL) construye.

La sección 5.10 retomará Spring Data como "siguiente paso natural" y será allí donde se contextualice todo el ecosistema.

## Resumen de la sección

- **Specifications** son una utilidad de Spring Data JPA, no de JPA estándar.
- Encapsulan **predicados reutilizables y combinables** sobre Criteria.
- Resuelven el problema de queries dinámicas **con mucha mejor ergonomía** que Criteria a pelo.
- Existen otras alternativas (QueryDSL, jOOQ, Blaze) que cubren nichos similares.
- En este curso solo las mencionamos: las verá el alumno en cuanto entre a Spring Data.

En 5.6 cerramos el repaso de mecanismos de consulta con **SQL nativo**: cuándo está justificado bajar del modelo a las tablas.
