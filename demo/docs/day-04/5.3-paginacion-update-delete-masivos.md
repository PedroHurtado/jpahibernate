# 5.3 · Paginación, `UPDATE` y `DELETE` masivos

## Listados que no caben en memoria

Hasta aquí todas las consultas devolvían toda la tabla. Eso es factible con 20 pizzas en H2 y desastroso con 200.000 comentarios en producción. El primer problema serio que aparece al escalar es la **paginación**.

JPA expone dos métodos en cualquier `Query` / `TypedQuery`:

```java
TypedQuery<CommentEntity> query = em.createQuery(
    "SELECT c FROM CommentEntity c ORDER BY c.fecha.valor DESC",
    CommentEntity.class
);
query.setFirstResult(20);   // offset
query.setMaxResults(10);    // límite

List<CommentEntity> pagina = query.getResultList();
```

`setFirstResult` indica cuántos resultados saltar; `setMaxResults`, cuántos devolver. El proveedor traduce esto al dialecto correspondiente: `LIMIT/OFFSET` en H2 y PostgreSQL, `FETCH FIRST` en Oracle moderno, `TOP` y subqueries en versiones antiguas de SQL Server. Esa traducción es uno de los argumentos a favor de usar JPQL en lugar de SQL nativo: el código del repositorio no cambia entre bases de datos.

## Detalles que duelen si no se conocen

**1. `ORDER BY` es obligatorio.** Sin orden explícito, paginar no tiene sentido: la base de datos no garantiza el orden de filas, así que la página 2 podría repetir filas de la página 1. Esto no falla, pero produce resultados aparentemente correctos y profundamente erróneos. Conviene aprenderlo antes que en producción.

**2. El `count` viene aparte.** Para mostrar "página 3 de 47" hay que ejecutar una segunda consulta:

```java
Long total = em.createQuery(
    "SELECT COUNT(c) FROM CommentEntity c", Long.class
).getSingleResult();

int totalPaginas = (int) Math.ceil(total / (double) tamanoPagina);
```

Spring Data JPA esconde esto detrás de `Page<T>`, pero la mecánica subyacente son dos queries: la de la página y la del total.

**3. Paginación + `JOIN FETCH` a colección no funciona bien.** Ya lo mencionamos en 5.2 y conviene reforzarlo aquí. Si el listado tiene que mostrar pizzas con sus ingredientes paginadas, la solución no es un único `JOIN FETCH` con `setMaxResults`. El patrón correcto es **dos pasos**:

```java
// Paso 1: traer SOLO los ids de la página
List<PizzaId> ids = em.createQuery(
    "SELECT p.id FROM PizzaEntity p ORDER BY p.nombre", PizzaId.class
).setFirstResult(20).setMaxResults(10).getResultList();

// Paso 2: traer las pizzas completas (con JOIN FETCH) filtradas por esos ids
List<PizzaEntity> pizzas = em.createQuery(
    "SELECT p FROM PizzaEntity p JOIN FETCH p.ingredientes " +
    "WHERE p.id IN :ids ORDER BY p.nombre",
    PizzaEntity.class
).setParameter("ids", ids).getResultList();
```

Dos queries en lugar de N+1 o el desastre de paginar en memoria. Es el patrón estándar y conviene fijarlo.

## El `OFFSET` no es gratis

Una nota que vale para cualquier base de datos relacional: `OFFSET 1000000 LIMIT 10` obliga al motor a recorrer 1.000.010 filas y descartar 1.000.000. En tablas muy grandes, paginación por offset es lineal en la página solicitada.

La alternativa profesional es **keyset pagination** (también conocida como *seek method*): paginar por un cursor (la última `fecha` y el último `id` vistos) en lugar de por offset. JPA no la facilita especialmente, pero JPQL la soporta sin problema:

```java
"SELECT c FROM CommentEntity c " +
"WHERE (c.fecha.valor, c.id) < (:ultimaFecha, :ultimoId) " +
"ORDER BY c.fecha.valor DESC, c.id DESC"
```

No es algo que el curso vaya a desarrollar en profundidad, pero conviene mencionar que existe: cuando un alumno se encuentre con que la página 50.000 va lenta, la solución no es "más índices", es **cambiar de modelo de paginación**.

## Operaciones masivas: `UPDATE` y `DELETE` en JPQL

Hasta aquí, la mutación pasaba por traer la entidad gestionada, modificarla y dejar que `dirty checking` hiciera el `UPDATE` al hacer `commit`. Para una entidad o unas pocas, es ideal.

Para **miles de filas**, no.

Imaginemos un caso real: subimos el IVA del 20% al 21%, lo que afecta al precio calculado de todas las pizzas. Pero en nuestro caso el precio es derivado, así que pensemos en otro escenario más realista: queremos marcar como `inactive` todos los usuarios que no han comentado en el último año.

Hacerlo cargando 50.000 usuarios al contexto de persistencia y modificándolos uno a uno es absurdo. JPQL ofrece `UPDATE` y `DELETE` directamente:

```java
int afectados = em.createQuery(
    "UPDATE UserEntity u SET u.activo = false " +
    "WHERE u.id NOT IN (SELECT DISTINCT c.user.id FROM CommentEntity c " +
    "WHERE c.fecha.valor > :limite)"
)
.setParameter("limite", LocalDateTime.now().minusYears(1))
.executeUpdate();
```

Cosas a notar:

**1. No hay `TypedQuery`.** Las queries de modificación devuelven el número de filas afectadas (`int`), no resultados. Por eso volvemos al `Query` plano y `executeUpdate()`.

**2. La query va directa a la base de datos, sin pasar por el contexto de persistencia.** Esto es lo más importante de la sección. Si tenemos un `UserEntity` cargado en el contexto y lanzamos un `UPDATE` masivo que también lo afecta, ese objeto en memoria **no se actualiza**. El estado de Java y el de la base de datos se desincronizan.

La consecuencia práctica:

```java
UserEntity user = em.find(UserEntity.class, userId); // cargado, gestionado

em.createQuery("UPDATE UserEntity u SET u.activo = false")
  .executeUpdate();

System.out.println(user.isActivo()); // ¡true! No refleja el cambio
```

Para evitar sorpresas, el patrón es: **hacer `em.clear()` antes (o después) del bulk update**. Esto limpia el contexto y obliga a recargar cualquier entidad consultada después. Es el precio de saltarse el contexto: pierdes la sincronización automática.

**3. Las cascadas no se aplican.** El `UPDATE`/`DELETE` masivo no dispara `@PrePersist`, `@PreUpdate`, `cascade = REMOVE` ni ningún callback. Si una pizza tiene comentarios con `cascade = REMOVE` y borramos la pizza con un `DELETE` masivo, los comentarios **quedan huérfanos** con FK rota. Si hay constraint `ON DELETE CASCADE` en la BD, la BD los borrará; si no, error de integridad.

Por eso `DELETE` masivo en JPQL es operación con riesgo. La regla:

> Si necesitas que se ejecuten reglas del dominio, callbacks o cascadas, **carga y borra entidad a entidad**. Si solo necesitas borrar filas y la BD se encarga de la integridad, **`DELETE` masivo**.

## Ejemplo concreto en el dominio

Limpiar comentarios viejos:

```java
em.getTransaction().begin();

int borrados = em.createQuery(
    "DELETE FROM CommentEntity c WHERE c.fecha.valor < :limite"
)
.setParameter("limite", LocalDateTime.now().minusYears(2))
.executeUpdate();

em.getTransaction().commit();
em.clear(); // por si había comments cargados en el contexto

System.out.println("Borrados: " + borrados);
```

`CommentEntity` no tiene hijos en cascada (es un agregado fuera del Pizza), así que el bulk delete es seguro. Si en el futuro añadiéramos `Respuesta` colgada de `Comment` con `cascade`, esta misma operación pasaría a ser peligrosa y habría que repensarla.

## El detalle de la transacción

`UPDATE`/`DELETE` masivos **necesitan transacción activa**. Si lo lanzamos sin `begin()`, en JPA puro se obtiene `TransactionRequiredException`. Lo mencionamos porque entronca con uno de los errores comunes que veremos en 5.8: "se me olvidó la transacción".

## Resumen de la sección

- **Paginación**: `setFirstResult` + `setMaxResults`, siempre con `ORDER BY` explícito.
- **El `count` va aparte**, en una segunda query.
- **Paginar con `JOIN FETCH` a colección**: patrón en dos pasos (ids primero, datos después).
- **Offset grande es lento**; existe *keyset pagination* para datasets enormes.
- **`UPDATE`/`DELETE` masivos en JPQL**: van directos a la BD, no pasan por el contexto.
- Después de un bulk, **`em.clear()`** para evitar desincronizaciones.
- **No disparan callbacks ni cascadas**: usar solo cuando esa pérdida es aceptable.
- Toda operación masiva exige **transacción activa**.
