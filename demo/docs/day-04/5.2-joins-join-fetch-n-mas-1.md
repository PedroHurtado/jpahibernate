# 5.2 · Joins, `JOIN FETCH` y el problema N+1

## Donde el ORM enseña los dientes

En 4.7 decidimos que `Pizza.ingredientes` se carga **eager** (forma parte del agregado) y que `Pizza.comments` se carga **lazy** (queda fuera). Esa decisión fue arquitectónica. Ahora vamos a ver el otro lado de la moneda: **cómo se traduce esa decisión a SQL cuando consultamos**, y por qué un mal join puede tumbar una base de datos en producción.

Esta es probablemente la sección más importante del Bloque 5. La mayoría de problemas de rendimiento con JPA no vienen de queries lentas, sino de **muchas queries rápidas**.

## El primer ejemplo inocente

Queremos mostrar el listado de comentarios con el nombre de su pizza:

```java
List<CommentEntity> comments = em.createQuery(
    "SELECT c FROM CommentEntity c", CommentEntity.class
).getResultList();

for (CommentEntity c : comments) {
    System.out.println(c.getTexto() + " — Pizza: " + c.getPizza().getNombre());
}
```

Aparentemente trivial. Lo que ocurre por debajo, en cambio, es esto:

```
SELECT * FROM comment;                       -- (1) consulta inicial
SELECT * FROM pizza WHERE id = 1;            -- (2) Hibernate resuelve c.getPizza() de la primera fila
SELECT * FROM pizza WHERE id = 2;            -- (3) ... de la segunda
SELECT * FROM pizza WHERE id = 5;            -- (4) ... de la tercera
SELECT * FROM pizza WHERE id = 1;            -- (5) ... otra vez la 1, ¿no debería estar cacheada?
...
```

**Una query para los comentarios + N queries para resolver la relación**. De ahí el nombre: **N+1**. Si hay 1.000 comentarios, son 1.001 viajes a la base de datos.

Y eso suponiendo que el cache de primer nivel (el contexto de persistencia) está activo, que ahorra repetir las que ya estaban gestionadas. Sin ese cache, sería incluso peor.

## Por qué pasa

Cuando una relación está marcada como `FetchType.LAZY` (lo está por defecto en `@ManyToOne`/`@OneToMany`/`@OneToOne` cuando lo configuramos así), JPA no carga el otro lado al traer la entidad. Crea un **proxy**: un objeto vacío que solo conoce su `id`. La primera vez que tocamos un método de ese proxy (`getPizza().getNombre()`), Hibernate dispara una query nueva para llenarlo.

En el bucle anterior, ese disparo ocurre **una vez por iteración**. La elegancia del ORM se vuelve en nuestra contra: el código Java se ve limpio precisamente porque la query queda escondida.

## La pregunta correcta

> "¿Cómo le digo a JPA: tráeme los comentarios **y a la vez** las pizzas a las que pertenecen, en una sola consulta?"

La respuesta es `JOIN FETCH`.

## `JOIN FETCH`: el join que sí carga

```java
List<CommentEntity> comments = em.createQuery(
    "SELECT c FROM CommentEntity c JOIN FETCH c.pizza", CommentEntity.class
).getResultList();
```

Y el SQL pasa a ser:

```sql
SELECT c.*, p.*
FROM comment c
INNER JOIN pizza p ON c.pizza_id = p.id;
```

Una sola query. Una sola ida y vuelta. Los comentarios devueltos tienen su `pizza` ya inicializada (no son proxies), así que `c.getPizza().getNombre()` no dispara nada.

### Diferencia conceptual: `JOIN` vs `JOIN FETCH`

Este punto causa confusión y conviene fijarlo:

```java
// JOIN normal: filtra, pero NO trae la entidad relacionada
"SELECT c FROM CommentEntity c JOIN c.pizza p WHERE p.nombre = :nombre"

// JOIN FETCH: filtra Y trae la entidad relacionada cargada
"SELECT c FROM CommentEntity c JOIN FETCH c.pizza p WHERE p.nombre = :nombre"
```

Sin `FETCH`, el join **se usa para condiciones**, pero `c.getPizza()` sigue siendo un proxy lazy. Cuando lo toquemos, otra query.

Con `FETCH`, el join **además** trae los datos y rellena el proxy. No habrá query adicional.

Regla mental: `JOIN` filtra, `JOIN FETCH` filtra y carga.

## Cuándo usar `JOIN FETCH`

Y, sobre todo, **cuándo no**.

`JOIN FETCH` resuelve el N+1, pero tiene su propio coste:

1. **Trae más datos.** Cargar siempre el agregado entero "por si acaso" desperdicia memoria.
2. **Las colecciones grandes provocan productos cartesianos.** Si una pizza tiene 8 ingredientes y 200 comentarios, `JOIN FETCH` de ambas produce 1.600 filas en bruto que Hibernate tiene que deduplicar.
3. **Solo una colección a la vez (en general).** Hibernate puede hacer `JOIN FETCH` sobre una colección por consulta. Pedirle dos suele lanzar `MultipleBagFetchException`. Para varias colecciones hay alternativas (`@EntityGraph`, dos consultas separadas), pero la regla pragmática es: una colección por query.
4. **Paginación y `JOIN FETCH` no se llevan bien.** Si pedimos `setMaxResults(10)` sobre una query con `JOIN FETCH` a una colección, Hibernate **trae todo en memoria** y pagina ahí. En el log saldrá un warning bien conocido: `HHH000104: firstResult/maxResults specified with collection fetch; applying in memory`. Para datasets grandes esto es desastroso.

Por eso `JOIN FETCH` se aplica con criterio, **caso por caso**, no como costumbre. La pregunta correcta no es *"¿lazy o eager?"* sino *"¿qué necesita este caso de uso?"*. Y la respuesta a esa pregunta vive en la query, no en la entidad.

## El caso del agregado Pizza

Recordemos la decisión del Bloque 2: `Ingrediente` está **dentro** del agregado Pizza. Eso se traducía en eager por defecto. Pero en la práctica eager-por-defecto es una mala idea: si la pizza aparece en un listado, ¿queremos sus 8 ingredientes para cada una? Probablemente no.

Mejor diseño: la entidad declara la relación como `LAZY` (decisión técnica de fondo) y cada caso de uso decide explícitamente si pedirla:

```java
// Listado para mostrar nombres y precios calculados: trae ingredientes
em.createQuery(
    "SELECT p FROM PizzaEntity p JOIN FETCH p.ingredientes",
    PizzaEntity.class
).getResultList();

// Ficha de pizza por id: trae también ingredientes
em.createQuery(
    "SELECT p FROM PizzaEntity p JOIN FETCH p.ingredientes WHERE p.id = :id",
    PizzaEntity.class
).setParameter("id", pizzaId).getSingleResult();
```

La regla práctica para nuestro dominio:

- **Entidades lazy por defecto.** Es el comportamiento más seguro.
- **El caso de uso decide qué traer.** Si necesito ingredientes, hago `JOIN FETCH`.
- **El agregado se carga junto cuando se va a operar sobre él.** Para mutar una pizza, traigo sus ingredientes; para listar nombres, no.

## `LEFT JOIN FETCH` cuando la relación puede no existir

`JOIN FETCH` es inner join. Si pedimos `SELECT c FROM CommentEntity c JOIN FETCH c.pizza` y un comentario tiene `pizza = null` (no debería en nuestro modelo, pero ilustra el caso), ese comentario **no aparecerá** en el resultado.

Para no perder filas:

```java
em.createQuery(
    "SELECT c FROM CommentEntity c LEFT JOIN FETCH c.pizza", CommentEntity.class
).getResultList();
```

`LEFT JOIN FETCH` trae también los comentarios cuya pizza es nula; en esos casos `c.getPizza()` será `null` y hay que tratarlo.

## El caso `@OneToOne` Comment → User

En 3.7 dejamos sembrado este caso. Si `CommentEntity` tiene un `@OneToOne` con `UserEntity` lazy, recorrer una lista de comentarios mostrando el nombre del autor **es N+1**, igual de claro. La solución es la misma:

```java
em.createQuery(
    "SELECT c FROM CommentEntity c " +
    "JOIN FETCH c.pizza " +
    "JOIN FETCH c.user",
    CommentEntity.class
).getResultList();
```

Aquí están dos joins a **relaciones a uno** (no colecciones), así que el doble `JOIN FETCH` no produce cartesianos y Hibernate lo acepta sin protestar. Sería distinto si una de ellas fuera una colección.

## Cómo detectar N+1 en desarrollo

Sin medir no hay diagnóstico. En el `persistence.xml` (o en la configuración programática del Bloque 4) hay que activar:

```xml
<property name="hibernate.show_sql" value="true"/>
<property name="hibernate.format_sql" value="true"/>
<property name="hibernate.use_sql_comments" value="true"/>
```

Con esto, cualquier query disparada se imprime. Si vemos una en un bucle, hay N+1.

Para producción la herramienta de cabecera es **Hibernate Statistics**, que cuenta queries por sesión y deja en claro si alguien se desmadró:

```java
SessionFactory sf = em.getEntityManagerFactory().unwrap(SessionFactory.class);
Statistics stats = sf.getStatistics();
stats.setStatisticsEnabled(true);
// ... ejecutar caso de uso ...
System.out.println("Queries ejecutadas: " + stats.getQueryExecutionCount());
```

Es una herramienta que conviene mencionar y que el alumno descubra por su cuenta cuando le toque depurar.

## Resumen de la sección

- **N+1** es el problema más común con ORM: una consulta inicial + N consultas para resolver una relación lazy en bucle.
- `JOIN FETCH` lo resuelve: filtra **y** carga en la misma query.
- `JOIN` sin `FETCH` solo sirve para condiciones; deja la relación lazy.
- `JOIN FETCH` a colecciones tiene costes: cartesianos, conflictos con paginación, una colección por query.
- Diseño recomendado: **relaciones lazy + cada caso de uso pide explícitamente lo que necesita**.
- `LEFT JOIN FETCH` cuando la relación puede no existir.
- Sin `show_sql` o sin Statistics no hay manera honesta de saber qué está pasando.

En 5.3 entramos en paginación y operaciones masivas, que abren su propio capítulo de matices.
